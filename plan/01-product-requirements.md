## 0. 文档说明

### 0.1 调研覆盖范围

本次登录态调研覆盖了以下功能：

- 首页、版块页、最新回复、最新主题、置顶、精华、投票、悬赏、抽奖、红包列表。
- 普通主题页、回复、引用关系、树形/平铺视图、收藏、支持、反对、点亮、打赏。
- 发帖页及普通、悬赏、投票、抽奖、红包五种主题类型。
- 个人主页、我的主题、我的回帖、通知、收藏、私信。
- 每日签到、积分与成长值、积分明细、邀请码生成及邀请记录。
- 头像、用户名、邮箱、简介、附件、回收站。
- 密码、TOTP 两步验证、Passkey、登录设备、第三方账号绑定、账号注销。
- 隐私设置、拉黑用户、隐藏/拉黑版块、个性设置、私有订阅源。
- 商家/中介认证的公开名录、论坛规则、RSS/SEO 与公开治理说明。

当前登录账号是普通会员，因此管理后台、版主工作台、商家审核后台等无法直接观察。本规划中的后台、审核、风控和运维功能是基于公开规则、前台行为和可靠论坛工程实践补全的需求，不代表对目标站内部实现的推断。

“登录态观察到的能力”仅表示看到了入口、表单、页面文案或只读结果，不代表已经验证额度扣减、并发原子性、随机开奖、退款、拉黑效果或后台权限。第 4 节带需求 ID 的条目是产品功能的唯一实施事实源；[`02-technical-architecture.md`](02-technical-architecture.md) 是技术选型、数据事实源、事务边界、搜索、迁移和灾备拓扑的架构事实源；[`03-manage-console.md`](03-manage-console.md) 只细化后台交互与权限流程；[`05-visual-brand-spec.md`](05-visual-brand-spec.md) 是视觉与品牌复制事实源；[`04-execution-roadmap.md`](04-execution-roadmap.md) 只是前四者的派生执行清单，不得反向覆盖产品、架构、后台或视觉契约。功能盘点、页面清单、流程和里程碑只用于索引这些需求，不应生成另一套规则。

### 0.2 优先级定义

| 标记 | 含义 |
|---|---|
| `M0` | 开发前必须明确的产品、合规或架构决策 |
| `MVP` | 首次公开测试必须具备，缺失会使阅读、发布、治理或恢复链路不成立 |
| `P1` | MVP 稳定后的增强阶段总称，不作为独立发布门禁；未细分时按所属领域归入 P1-A（信任/留存/内容/治理）或 P1-B（商业） |
| `P1-A` | 信任与留存：完整信任/信誉、积分、签到、私信、投票和悬赏 |
| `P1-B` | 商业供给：商家认证、结构化交易、优惠、投诉和评价 |
| `P2` | 社区稳定后建设的高风险、强审计能力；核心是抽奖、红包、兑换码及其风控与冲正，也包括单独验收的高级治理/商业扩展 |
| `P2/Later` | P2 验收后再评估的开放生态与受控 AI；暂不承诺开放日期 |
| `Later` | 暂不承诺，只保留设计接口或研究项 |

### 0.3 规划原则

1. 先形成有价值的讨论，再增加游戏化和商业功能。
2. 公开阅读、邀请码注册、邮箱验证后发言，兼顾搜索流量和内容供给质量。
3. 身份角色、社区信誉、可消费积分三者分离。
4. 活动热度与内容质量分开统计、分开排行。
5. 交易和认证提供信息与信任辅助，首版不托管资金、不担保履约。
6. 所有积分、处罚、认证和活动结果都有不可篡改的流水或审计记录。
7. SSR 优先，保证首屏、SEO、无障碍和弱网络体验。
8. 高风险功能必须有独立开关，可以暂停注册、邀请、积分消费、交易发布和活动领取。
9. PostgreSQL 是结构化业务事实源；核心状态、审计、幂等结果和 Outbox 同事务提交，Redis 只做可丢失、可重建的加速与协调。

## 1. 产品定义

### 1.1 已批准定位

建立一个面向中文技术用户的垂直社区，首期聚焦以下交叉领域：

- AI 工具、工程实践与自动化。
- 域名、主机、网络与基础设施。
- 技术问答、经验复盘和资源分享。
- 有明确规则的优惠与二手交易信息。

项目定位已确认为：

> 面向独立开发者和海外 IT 从业者的 AI、域名与云基础设施实战社区。

### 1.2 目标用户

- 游客：通过搜索、RSS 或外部链接阅读内容。
- 新成员：通过邀请加入，希望快速了解规则并获得首次有效回复。
- 内容贡献者：发布教程、测评、复盘和高质量回答。
- 问题提出者：寻求可执行的解决方案。
- 商家与服务提供方：发布结构化优惠、产品信息和售后说明。
- 版主与运营：维护内容秩序、处理举报、组织内容和活动。

### 1.3 果农指数

果农指数为“每周有效贡献者数”，采用 UTC 自然周，月汇总采用 UTC 自然月（`DEC-049`）；自然周起点待用户明确，不使用滚动 7/30 天。满足以下任一条件且去重：

- 发布一篇非活动、非广告、通过审核的有效主题。
- 发布三条被不同可信用户认可的实质回复。
- 回答被采纳、帖子进入精华，或完成一次有效治理贡献。

辅助指标：

- 首次有效回复中位时间。
- 24 小时无有效回复主题比例。
- 非活动内容的 W1/W4 留存。
- 搜索访问到阅读、收藏、注册、回复的转化。
- 有效回复率、采纳率、收藏率、精华率。
- 抽奖/红包/推广内容在首页曝光和回复中的占比。
- 每千帖举报量、举报成立率、处理时长、申诉改判率。
- 邀请来源的激活率和 W4 留存。
- 商家内容过期率、投诉率和问题解决率。

#### MVP 计算口径

果农指数与部分辅助指标引用了 P1-A 才存在的信任快照、采纳与活动标记。MVP 期按下列可实现定义计算，阶段能力上线后自动收敛为完整定义，口径切换须在 `99` 登记：

| 概念 | MVP 口径 | 完整口径 |
|---|---|---|
| 可信用户 | 已通过邮箱验证、达到 T1 且无生效处罚；不设账号年龄阈值（`DEC-048`） | T2 及以上叠加信誉权重（P1-A `TRUST-003`） |
| 有效主题 | 通过审核、非活动、非广告，且正文至少 10 个英文字符（`DEC-049`；中文及其他 Unicode 字符折算待明确） | 叠加质量分与精华判定 |
| 实质回复 | 非纯引用、非纯表态，至少 2 个英文字符（`DEC-049`；中文及其他 Unicode 字符折算待明确），且被不同可信用户正向反馈 | 叠加可信反馈阈值（P1-A `SOCIAL-102`） |
| 采纳 | MVP 无采纳能力，该项恒计 0 并在看板显式标注「随 `TOPIC-103` 启用」 | `TOPIC-103` 采纳事件 |
| 非活动内容留存 | MVP 无抽奖/红包（属 P2），等同全量 W1/W4 留存 | 排除活动参与后的留存 |


### 1.4 已批准视觉与品牌基线

- 视觉风格与品牌标识严格复制 [`sb.sb`](https://sb.sb/) 的公开可观察界面，含 Logo/文字标识、favicon、品牌主色、字体、图标语言、间距、圆角、边框、信息密度、明暗主题和响应式布局。
- “严格参考”在本项目中明确等于复制品牌标识，不是灵感参考；项目名称为“草莓社区”，公开页头文字标识使用“草莓论坛”。
- 运行时不热链参考站资源；本轮 A00 采集限定调整按 `DEC-046` 执行。
- 唯一视觉实现与截图验收契约见 [`05-visual-brand-spec.md`](05-visual-brand-spec.md)。

### 1.5 首版明确不做

- 现金充值、提现、现金红包或积分兑换法币。
- 平台担保交易、代收款、资金托管和强制仲裁赔付。
- 付费参与的抽奖或任何类似博彩的机制。
- 无审核匿名发帖。
- 积分自由转账或公开买卖。
- 自动参与全部讨论的 AI 账号。
- 原生 iOS/Android 客户端。
- 用户自建版块、复杂群组或插件市场。
- 一开始就开放十几个没有稳定内容供给的版块。

## 3. 角色、身份与权限

角色决定职责，信任等级决定发布额度，两者不能用一个“等级”字段替代。

### 3.1 系统角色

| 角色 | 主要权限 |
|---|---|
| 游客 | 阅读公开内容、搜索、查看公开资料、申请注册 |
| 待验证用户 | 完成邮箱验证和邀请绑定，不能公开发布 |
| 普通会员 | 发主题、回复、收藏、关注、举报、管理本人资料和内容 |
| 可信会员 | 更高额度、较少预审、创建少量邀请、参与共治功能 |
| 认证商家 | 普通会员权限，加结构化商家主页和商业内容发布能力 |
| 版主 | 管理指定版块的内容、举报和临时限制 |
| 全局版主 | 跨版块审核、处罚、申诉、商家材料初审 |
| 客服 | 处理账号与认证工单，不能修改积分或处罚证据 |
| 风控运营 | 查看风险摘要、冻结高风险操作，不能编辑内容正文 |
| 活动运营 | 创建和审核活动，不能直接修改积分账本 |
| 管理员 | 用户、角色、版块、配置、功能开关和审计查询 |
| 站点所有者 | 密钥、账单和生产访问等极高危能力 |
| 只读审计员 | 查看审计与统计，不能执行写操作 |
| 系统账号/机器人 | 发布系统消息，不参与积分、榜单、活动和交易评价 |

### 3.2 信任等级

| 等级 | 条件示例 | 权益示例 |
|---|---|---|
| T0 新成员 | 已验证但贡献不足 | 严格限频、外链/附件受限、首帖可预审 |
| T1 正常成员 | 跨天活跃并有有效贡献 | 标准发帖、回复、收藏和举报额度 |
| T2 可信成员 | 账号年龄、有效贡献、低违规率达到门槛 | 少量邀请、更高发布额度、降低审核摩擦 |
| T3 社区贡献者 | 长期高质量贡献和治理记录 | 标签整理、重复主题标记、社区协助能力 |

信任等级降级必须记录原因、通知用户并支持申诉。认证商家、版主和管理员仍有独立角色，不可仅凭信任等级自动获得。

### 3.3 权限矩阵最低要求

| 动作 | 游客 | 待验证 | 普通会员 | 可信会员 | 商家 | 版主 | 管理员 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 阅读公开主题 | 是 | 是 | 是 | 是 | 是 | 是 | 是 |
| 阅读仅会员主题 | 否 | 否 | 是 | 是 | 是 | 是 | 是 |
| 发主题/回复 | 否 | 否 | 是，限频 | 是 | 是 | 是 | 是 |
| 上传附件 | 否 | 否 | 限制 | 是 | 是 | 是 | 是 |
| 创建邀请 | 否 | 否 | 否/少量 | 是 | 是 | 是 | 是 |
| 发布交易/优惠 | 否 | 否 | 功能上线且达门槛后 | 功能上线且达门槛后 | 认证范围内 | 不因职务获得 | 不因职务获得 |
| 创建活动 | 否 | 否 | 否 | 功能上线后可申请 | 功能上线后可申请 | 不因职务获得 | 不因职务获得 |
| 处理举报 | 否 | 否 | 否 | 可标记 | 否 | 授权版块 | 是 |
| 调整积分 | 否 | 否 | 否 | 否 | 否 | 否 | 仅冲正/审批 |
| 修改站点配置 | 否 | 否 | 否 | 否 | 否 | 否 | 是 |

所有权限必须在服务端检查。隐藏按钮不能代替鉴权；管理后台采用默认拒绝、最小权限和资源级授权。

员工职务角色与会员行为身份分离：版主、客服、风控、活动运营、管理员、所有者和审计员不会因职务自动获得邀请、交易、活动参与或内容推广权益。每个后台角色按资源范围、所有权、信任门槛和临时授权单独测试；任何人不得审批自己的认证、活动、处罚、提权或积分调整。

后台采用“RBAC 能力上限 + ABAC 资源范围”，每个管理会话一次只激活一个职务角色分配。角色、范围、会话撤销事实与 `authz_version` 保存在 PostgreSQL；写命令必须携带当前分配和权限版本，陈旧权限上下文一律拒绝。敏感读取必须在同一短 PostgreSQL 事务内完成重新授权与追加式审计，审计写入失败时不返回数据。

#### 后台职责矩阵

| 角色 | 默认资源范围 | 可执行动作 | 可审批 | 明确禁止 |
|---|---|---|---|---|
| 版主 | 被授权版块的内容与举报 | 内容处置、临时限制、证据快照 | 否 | 查看商家材料、积分调整、全站配置 |
| 全局版主 | 全站内容、处罚与申诉 | 跨版块处置、处罚、独立申诉复核 | 非本人处理的申诉 | 商家终审、积分调整与密钥 |
| 客服 | 指派给本人的支持工单 | 用户沟通、低风险资料更正、升级工单 | 否 | 单人恢复 MFA、修改处罚证据、查看积分密钥 |
| 风控运营 | 风险事件、必要的伪匿名信号 | 冻结高风险能力、提交复核 | 风险规则灰度申请 | 编辑正文、改账本、读取无关私信或证件 |
| 活动运营 | 已批准活动及其预算摘要 | 创建活动草案、执行批准后的活动 | 不能审批本人活动 | 直接改账本、选择中奖者、删除处罚 |
| 管理员 | 用户、角色、版块、配置与系统运行 | 授权范围内配置和运维操作 | 非本人高危申请的第一/第二审批 | 静默改账本、删除审计、读取明文密钥 |
| 站点所有者 | 生产、密钥、账单与灾备 | 极高危运维、break-glass | 按双人规则审批 | 使用所有者账号参与日常社区或自批 |
| 只读审计员 | 脱敏审计、指标和审批记录 | 查询、验证完整性、出具审计结论 | 否 | 任何生产写入、导出无关原始敏感资料 |

冷启动人员规模下（`DEC-003-A`：1 名管理员、0 名版主），双人审批与职责分离由站点所有者充当第二审批人；所有者的审批动作单独标记、写入审计并触发告警，这是「所有者不参与日常社区操作」的唯一例外，不得扩展到日常内容处置。

上线前另行固化机器可读 RBAC 规格，列出资源范围、所有权条件、前置 MFA、临时授权期限和冲突角色；本表是最低边界，不替代服务端策略与自动化权限测试。

### 4.11 签到、积分、信誉、等级与徽章

#### 核心设计

- 可消费积分：用于悬赏、打赏和后续活动，只能由账本产生。
- 社区信誉：反映长期高质量贡献，不因消费积分下降。
- 信任等级：由账号年龄、验证、质量、违规和风险综合决定，不等于信誉数字。
- 徽章：表达特定贡献，不授予后台权限。

#### MVP

- [ ] `TRUST-001` MVP 只启用可解释、版本化的 T0/T1 发布门槛快照，不直接复用信誉或积分余额；T2/T3、自动升降级和完整信誉体系保持关闭到 P1-A。

#### P1-A

- [ ] `TRUST-002` 支持按确定性规则计算、重算和降级信任等级；自动结果可由授权人员复核，但人工覆盖必须有原因、期限和审计。
- [ ] `TRUST-003` 可信反馈、亮回复和邀请额度只读取已落库的信任快照，规则变化后可批量重算且不追溯篡改历史事件。
- [ ] `TRUST-004` 人工授予或撤销可信身份采用资源级权限，不能由用户本人或存在利益关系的员工审批，并支持申诉。
- [ ] `REP-001` 记录有效贡献事件，但首版可以只展示信誉摘要，不开放复杂消费。
- [ ] `REP-002` 原始发帖次数、回帖次数和签到不直接无限增加信誉。
- [ ] `REP-003` 信誉事件包括回答被采纳、进入精华、获得多个可信用户认可和终审成立的治理贡献；治理贡献不公开具体举报对象。
- [ ] `REP-004` 个人主页展示信誉等级和贡献构成，不展示风控内部评分。

- [ ] `POINT-101` 建立 `PointAccount`、`PointTransaction`、`PointEntry` 不可变账本。
- [ ] `POINT-102` 每个业务事件使用唯一幂等键；分录不可修改或删除，只能冲正。

### 4.22 风控与反作弊

#### MVP

- [ ] `RISK-001` MVP 的注册、登录、邀请、发帖、回复和反馈统一产生标准化 `RiskEvent`；私信、交易和活动在各自上线前必须接入同一事件契约。
- [ ] `RISK-002` 每次风险决策记录规则版本、命中信号、处理动作和可解释摘要。
- [ ] `RISK-003` 账号、IP、设备、网络段、邀请关系和行为时间序列只作为组合信号，不用单一 IP 自动封禁。
- [ ] `RISK-004` 按风险逐级采取限速、验证码、冷却期、待审、延迟奖励、人工复核、功能冻结和封禁。
- [ ] `RISK-005` 新账号的外链和附件采用独立门槛；私信、交易和活动在各自上线时必须配置独立门槛，不能沿用普通发帖额度。
- [ ] `RISK-006` 检测重复文本、批量注册、自赞、互刷、删除重发、邀请闭环和短时间机械操作。
- [ ] `RISK-007` 风控数据使用最少必要、哈希或伪匿名标识，并在隐私政策中披露用途。
- [ ] `RISK-008` 风控服务不可用时，阅读继续可用；注册以及当时已启用的领奖、商家发布等高风险操作失败关闭。

#### P1

- [ ] `RISK-101` 统一风险规则引擎，规则支持版本、灰度、命中解释、回放和误伤监控。
- [ ] `RISK-102` 建立账号、设备、邀请、互动、交易和活动关系图，识别团伙作弊和协同诈骗。
- [ ] `RISK-103` 风险挑战编排支持验证码、邮箱二次确认、重新认证、延迟到账和人工复核。
- [ ] `RISK-104` 举报人可信度、商家投诉率、评价集中度和邀请 cohort 质量进入风险信号。
- [ ] `RISK-105` 建立抽样质检、误判率、漏判率、申诉改判率和群体差异监控。

#### P2

- [ ] `RISK-201` 图分析或机器学习仅用于复杂团伙识别，输出必须可解释、可回放、可人工覆盖。
- [ ] `RISK-202` Just-in-Time 生产访问、临时提权、完整管理员会话审计和自动到期。

#### 验收标准

- 风控决定不能直接修改账本历史，只能冻结、延迟或创建冲正事务。
- 用户能获得适度、可申诉的限制说明，但内部检测细节不暴露给攻击者。
- 风险规则变更有审批、回滚和效果对比，不能直接无记录修改生产规则。
- 误伤共享网络用户、正常高活跃用户和无障碍工具用户的场景必须纳入测试。

## 5. 关键用户流程

### 5.1 邀请注册与首次贡献

1. 游客通过搜索、RSS 或分享链接阅读公开主题。
2. MVP 填写邀请码、用户名、邮箱、密码并同意当前规则版本；P1 启用第三方登录后，可选择经重新认证保护的第三方账号。
3. 系统完成人机验证和风险检查，在一个 PostgreSQL 事务中锁定 `bcm_identity.invitations` 并校验资格，创建待验证用户、同意记录、验证记录、`bcm_trust.invite_uses`、风险事件和邮件 Outbox。
4. 用户通过邮箱链接完成验证；请求重试复用原幂等键，不重复注册或消费邀请码。
5. 引导用户选择感兴趣版块、阅读精选内容和社区规则。
6. 用户发布首次回复或主题；高风险内容进入待审。
7. 内容公开后，由已提交 Outbox 驱动通知和统计。
8. 达到跨天活跃和有效贡献条件后，邀请关系变为“有效”，在同一账本事务中奖励邀请人。

验收：刷新和重试不重复注册或消耗邀请码；待审内容仅本人和审核员可见；邀请奖励可以冲正。

### 5.2 发布主题并获得答案

1. 用户选择版块和主题类型。
2. 系统加载该版块模板、规则和结构化字段。
3. 用户填写标题、正文、标签和访客可见性。
4. 系统提示相似主题、敏感信息和内容风险。
5. 用户保存草稿、预览并发布；服务端校验权限和正交状态。创建主题时初始化楼层计数器和首帖；新增回复时锁定主题行并用专用计数器分配 `floor_no`，禁止 `MAX()+1`。帖子、不可变修订、计数、`search_documents`、Outbox 及适用的审计记录在同一 PostgreSQL 事务提交。
6. 关注主题并收到回复、提及和引用通知。
7. 作者采纳答案或版主标记已解决。
8. 采纳和可信反馈产生信誉事件及可选积分奖励。

### 5.3 举报、处理与申诉

1. 用户选择举报原因并补充说明或证据。
2. 系统生成证据快照、合并重复举报并进入队列。
3. 版主调查并提交内容级或账号级措施；状态迁移、证据引用、审批版本、`audit_events`、幂等结果和 Outbox 在同一 PostgreSQL 事务提交。
4. 被处理用户收到处罚范围、期限和规则依据。
5. 用户在期限内提交申诉。
6. 非原处理人复核并完成终审。
7. 结果进入审计和治理统计。

### 5.4 积分奖励与消费

1. 用户行为产生标准领域事件。
2. 规则引擎检查资格、日限额、关联账号和风险状态。
3. 在同一数据库事务中锁定相关账户，创建业务状态、幂等记录、平衡账本分录和 Outbox 事件；任一步失败则全部回滚。
4. 余额投影与账本分录、业务状态在同一事务更新且可由分录重建；提交后 Outbox 只触发通知、统计和外部投影等副作用。
5. 通知和统计异步处理。
6. 行为撤销、作弊确认或活动取消时创建冲正事务。

### 5.5 商家认证与发布优惠

1. 用户提交商家申请和最少必要材料。
2. 审核员核验并记录范围、证据、到期日和结果。
3. 认证商家使用结构化模板发布优惠或交易信息。
4. 页面展示价格、有效期、推广关系、认证范围和风险提示。
5. 用户收藏、反馈、投诉或自报成交。
6. 到期自动标记，认证和内容分别进入复审。

### 5.6 账号安全与注销

1. 用户查看当前设备和其他登录会话。
2. 可撤销单一会话或退出其他设备。
3. 修改密码、邮箱、MFA 或 Passkey 时重新认证。
4. 注销需当前密码、邮件确认和 7 天冷静期。
5. 冷静期内可登录撤销；期满后先写入删除墓碑并检查法律保留，再执行匿名化/删除策略。
6. 账本、审核证据和法定记录按最少必要字段保留；Worker 将删除传播到缓存、S3 和分析投影，灾备恢复后先重放墓碑再开放流量。

## 6. 核心数据模型

全部结构化业务实体均持久化到 PostgreSQL 16，并按 bounded context 放入带部署前缀的 schema；Redis 不保存下表实体的权威状态。逻辑实体名用于产品沟通，物理 schema、标识符、约束和迁移规则以第 7 节及 [`02-technical-architecture.md`](02-technical-architecture.md) 为准。

|---|---|
| `platform` / 平台 | `OutboxEvent`、`IdempotencyRecord`、`Job`、`JobAttempt`、`SinkDelivery`、`WebhookDelivery`、`OperationRun`、`FeatureFlag`、`CursorKey`、`SchemaMigration` |
| `identity` / 身份 | `User`、`UserProfile`、`Credential`、`Invitation`、`EmailVerification`、`Session`、`OAuthAccount`、`Passkey`、`TotpMethod`、`RecoveryCode`、`ConsentRecord` |

| `interaction` / 互动 | `Reaction`、`Bookmark`、`Subscription`、`ReadState`、`Follow`、`BlockRelation`、`Notification`、`NotificationPreference`、`EmailDelivery`、`EmailSuppression`、`MessageThread`、`Message` |
| `trust` / 信任与风控 | `TrustProfile`、`InviteUse`、`InviteQualification`、`InviteReward`、`PointAccount`、`PointTransaction`、`PointEntry`、`ReputationEvent`、`BadgeAward`、`SignIn`、`RiskEvent`、`RiskDecision` |
| `campaign` / 活动 | `Poll`、`PollOption`、`PollVote`、`Bounty`、`BountySettlement`、`RewardCampaign`、`CampaignRuleVersion`、`CampaignBudgetReservation`、`EligibilitySnapshot`、`RandomnessCommitment`、`LotteryPrize`、`LotteryEntry`、`PrizeCode`、`RewardClaim`、`RedPacketShare` |

统一数据约定：URL 资源使用 PostgreSQL `BIGINT IDENTITY`，Rust 拒绝负值并在 JSON/API 中以十进制字符串传输；事件和操作使用 UUIDv7；时间使用 UTC `timestamptz`；状态一律使用文本，由服务层白名单校验，并以 `CHECK` 约束作为数据库侧第二道防线（PostgreSQL、SQLite 与 MySQL 8.0.16+ 均真实生效，`DEC-033`）；高频查询字段使用列式类型，规则、风险信号和扩展载荷以 `TEXT` 存储 JSON 并在应用层解析校验，不使用 `JSONB` 运算符（`DEC-022`）。会话、邀请码、恢复码和访问令牌只保存随机值的哈希或密文；注销保留最小用户存根，账本、审计、证据和回复结构使用 `RESTRICT`，禁止级联破坏。

### 6.1 必须维持的不变量

- 每个业务事件有唯一幂等键；请求重放、队列重试和并发点击不能重复记账。
- 每个邀请码、投票资格、红包份额、抽奖资格和悬赏结算只能成功消费一次。
- 主题、回复、认证、活动和处罚引用当时生效的规则版本。
- 主题发布、审核、讨论、可见性、删除和归档是正交状态；所有迁移必须通过显式服务端状态机。
- 版块权限、作者默认可见性和主题选择冲突时采用最严格权限；派生缓存、搜索、RSS 和分享摘要不得放宽源对象权限。
- 内容软删除、用户封禁和账号注销不能破坏回复结构和证据。
- 认证原始材料、兑换码、恢复码和访问令牌使用独立密钥或字段级加密。
- 高危审批禁止自提自批；审批后载荷变化必须使原批准失效。

### 6.2 关键索引

本节全部为普通 B-tree 复合索引；`DEC-022` 全局禁用部分索引，过滤列一律进入索引键。物理名以 PostgreSQL 完整模式书写，SQLite/MySQL 的扁平表名由 `SchemaRenderer` 渲染。

- `bcm_community.topics(forum_id, last_post_seq DESC, id DESC)`：版块最新回复流。
- `bcm_community.topics(forum_id, created_seq DESC, id DESC)`：版块最新主题流。
- `bcm_community.posts(topic_id, floor_no)`：楼层定位与分页；楼层号由锁定主题行后的专用计数器生成，禁止 `MAX()+1`。
- `bcm_interaction.notifications(user_id, read_at, created_at DESC, id DESC)`：未读通知（`read_at` 进入索引键而非 `WHERE` 子句——`DEC-022` 全局禁用部分索引）。
- `bcm_identity.invitations(code_hash)` 唯一，`bcm_identity.invitations(creator_id, status, created_at)`：邀请码与注册凭据查询；消费、资格和奖励记录使用 `bcm_trust.invite_uses` 等信任域表。
- `bcm_trust.point_entries(account_id, created_at, id)`；积分业务事件、活动参与、悬赏结算和红包份额均设置唯一约束。
- `bcm_moderation.reports(status, priority, created_at)`：审核队列。
- `bcm_commerce.trade_listings(status, category, expires_at)`：有效商业内容。
- 规范化用户名、邮箱、邀请码哈希、互动关系、投票、领取、结算和业务事件均建立唯一约束。
- `bcm_community.search_documents` 必须携带实体版本、可见性、版块权限、审核和删除状态；正文词项使用 `pg_jieba` GIN 索引，标题使用 `pg_trgm`。用户名模糊匹配直接查询 `bcm_identity.users` 的规范化列与 `pg_trgm` 索引，不把身份资料复制进内容搜索表。
- 核心 `topics/posts` 首版不分区；`audit/analytics` 及风控数据达到已批准容量阈值后再按月分区或归档。

## 7. 确定技术架构

本项目已确定采用 [`02-technical-architecture.md`](02-technical-architecture.md) 的 PostgreSQL + Redis + `sqlx` 架构，不再把 Discourse、Flarum、Laravel、Meilisearch 或 OpenSearch 作为并行候选。技术选型、数据事实源、事务、搜索、迁移和灾备决策冲突时以该架构文档的已决约束为准。合并时仓库没有可验证的应用代码或迁移；后续覆盖范围统一登记在 [`99-traceability.md`](99-traceability.md)，不得把规划路径或契约草案误报为端到端发布能力。

### 7.1 技术基线

- Rust + Axum 提供 HTTP 服务，Askama 完成 SSR，交互使用少量 TypeScript；首版保持模块化单体，并独立部署 `bbbcm-worker`。
- 双部署形态：PostgreSQL 16 完整模式与 SQLite 单文件体验模式（功能降级边界见 `02` 第 6 节）；后端由 `database.backend` 配置决定，不提供跨后端数据迁移。SQL 按 PostgreSQL 16 + SQLite + MySQL 8.0 三库交集子集编写（DEC-022），后续支持 MySQL 8.0 零返工（现在不实现）。
- PostgreSQL 16 单主实例是全部结构化业务数据的唯一事实源。
- Redis 8 只承担缓存、会话校验加速、限流、短租约和任务唤醒；Redis 丢失、重启或清空不得造成业务数据损失。
- `sqlx 0.8+` 是唯一数据库访问层；所有值使用绑定参数，schema/table 标识符只允许由受信注册表和已校验前缀生成。
- 主搜索固定使用 PostgreSQL `pg_jieba + pg_trgm`，不部署独立全文搜索服务；权限与可见性过滤在同一 PostgreSQL 查询内完成。
- S3 兼容对象存储保存附件和证据；Cloudflare 提供 CDN/WAF，SMTP、OAuth 与 Cap.js 作为外部依赖。
- 功能按 MVP、P1-A、P1-B、P2、P2/Later 分阶段启用；高风险功能默认关闭，不因代码已部署而提前开放。

### 7.2 模块与 PostgreSQL schema

逻辑域和数据库 schema 一一对应：

| 逻辑 schema | 职责 |
|---|---|
| `platform` | Outbox、幂等记录、任务、操作运行状态、功能开关、迁移元数据和游标密钥 |
| `identity` | 用户、邀请码、凭证、验证、会话、OAuth、MFA 与 Passkey |
| `iam` | 角色、权限、分配、资源范围、员工身份投影、管理会话、审批与权限版本 |
| `community` | 版块、主题、回复、修订、标签、草稿与搜索文档 |
| `media` | 附件、隔离扫描、变体、引用、回收站与证据对象 |
| `interaction` | 收藏、反馈、关注、拉黑、阅读状态、通知与私信 |
| `trust` | 邀请使用/资格/奖励、信任等级、信誉、积分账本、签到、徽章、风险事件与决策 |
| `campaign` | 投票、悬赏、抽奖、红包、资格、预算与结算 |
| `commerce` | 商家认证、交易、优惠、评价与争议 |
| `moderation` | 举报、案件、处罚、申诉、证据与规则版本 |
| `support` | 工单、消息、恢复申请、队列与 SLA |
| `privacy` | 数据请求、隐私导出任务、法律保留、删除墓碑与传播状态 |
| `operations` | 后台配置、工作项、批量快照与维护模式 |
| `audit` | 仅追加审计事件与敏感访问记录 |
| `analytics` | 指标定义、聚合投影、水位与排除规则 |

- 配置项 `database.schema_prefix` 默认且生产固定为 `bcm_`，物理 schema 使用 `<schema_prefix><logical_schema>`，例如 `bcm_identity.users`、`bcm_platform.outbox_events`。
- 前缀必须以 ASCII 小写字母开头，只含 `[a-z0-9_]`，以 `_` 结尾且不超过 32 个字符；拼接后的 PostgreSQL 标识符不得超过 63 个字符。前缀是部署级配置，禁止来自请求或租户输入，初始化后只能在维护窗口显式迁移。
- 迁移元数据表固定为 `<schema_prefix>platform.schema_migrations`，当前即 `bcm_platform.schema_migrations`，不使用默认 `_sqlx_migrations`。
- Rust workspace 按平台与领域组织 `contract/core/repo/http/jobs` 边界；HTTP handler 不直接写 SQL，跨领域副作用通过已提交 Outbox 协作。

### 7.3 数据访问与事务边界

- Handler 只负责解析、CSRF、鉴权和响应；应用服务经 `platform-db` 的统一事务模板取得当前后端的事务连接，Repository 只借用该连接，不得自行从连接池开启事务。连接类型是后端无关的封装，不在领域层出现 `PgConnection` 等方言类型（`DEC-022`，见 `02` 第 6.1 节）。
- 一次命令涉及的业务状态、唯一约束、实体版本、`bcm_platform.outbox_events` 和幂等结果必须在同一事务提交。
- PostgreSQL 完整模式：默认隔离级别 `READ COMMITTED`；竞争点按固定顺序 `FOR UPDATE`，必要时使用 `SERIALIZABLE`；对 `40001` 和 `40P01` 最多有界重试 3 次，`lock_timeout` 设为 500ms。SQLite 体验模式：单写者 + WAL + `BEGIN IMMEDIATE`，`busy_timeout` 5000ms，不做序列化重试。MySQL 8.0 接入时另定。行锁语法只出现在 `platform::db` 的方言分支（`DEC-022`）。
- 写命令统一包含 `actor_id`、`request_id`、`idempotency_key`、`expected_entity_version`、`expected_actor_authz_version` 和类型化载荷；后台命令另含 `active_assignment_id`、`reason_code`、`ticket_id`。
- `If-Match` 对应实体 `version`；版本更新影响行数为 0 时返回 `409`。幂等记录以 `(scope, actor_id, key)` 唯一，同请求哈希返回原响应，不同载荷返回 `409`；`operation_id` 在提交前生成并随事务写入，提交阶段连接断开时返回 `202` 和该 ID，状态查询仍必须携带原幂等键。普通幂等响应默认保留 30 天，邀请、积分、处罚、角色变更和活动资格的业务唯一记录按保留矩阵长期保存或归档。
- URL 资源使用自增主键（PostgreSQL `BIGINT IDENTITY`；三库映射见 `02` 第 6.2 节），API 以十进制字符串传输；事件和操作使用应用层生成的 UUIDv7，时间统一为 UTC。可查询字段使用列式类型，规则、风险信号和扩展载荷以 `TEXT` 存储 JSON 并在应用层解析（`DEC-022`）。
- 数据库迁移通过 `bbbcm-cli db migrate` 执行；索引随 N 轨迁移以普通 `CREATE INDEX` 创建（`DEC-022` 的可移植子集不含 `CONCURRENTLY`，且它不能在事务型迁移内执行）。PostgreSQL 生产环境为既有大表补建索引时的 `CONCURRENTLY` 流程属运维手册，见 `91`。

### 7.4 Outbox、Redis、搜索与附件

- `bcm_platform.outbox_events` 是可靠事件源。Worker 使用 `FOR UPDATE SKIP LOCKED` 批量租约，失败指数退避并最终进入 DLQ；每个外部 sink 以 `(sink, event_id)` 唯一去重。
- 邮件、通知、媒体、统计和 Webhook 只能消费已提交 Outbox，不得异步补做积分、权限、资格或其他核心业务事实。Redis Pub/Sub 或 Stream 只作低延迟唤醒，丢失后由 PostgreSQL 轮询恢复。
- Redis 键使用 `bcm:<env>:v1:<domain>:<kind>:<id>` 前缀（仅 `features.redis=true` 时装配）。公开片段缓存默认 TTL 30 秒，键包含实体版本和可见性维度，私有内容不共享缓存；缓存失效在 PostgreSQL 提交后执行并由 Outbox 重试。删除、封禁、权限收紧期间以及后台、高危写始终回查主库。限流由 Redis 承载，键在 `bcm:<env>:v1:ratelimit:` 命名空间下；`features.redis = false` 时不提供限流能力（`DEC-024`）。
- Redis 不可用时，普通公开读取回源 PostgreSQL；注册、领奖和高风险操作的限流失败关闭。`SET NX PX` 只防重复执行或缓存击穿，业务正确性始终依赖 PostgreSQL 锁与约束。
- `bcm_community.search_documents` 与内容可见性状态同事务更新；搜索使用 `pg_jieba` GIN 索引和 `pg_trgm` 模糊匹配，并在 PostgreSQL 内完成版块、拉黑、审核和删除过滤。结果使用相关度与 ID 组成的签名 keyset cursor。SQLite 体验模式仅标题检索（FTS5 探测，不可用时规范化标题 LIKE）。
- 附件先在 PostgreSQL 建立 `pending/quarantine` 记录并上传隔离 S3；扫描、解码或转码成功后才允许内容引用，孤儿对象由定时任务回收。
- `bcm_audit.audit_events` 仅允许追加，应用角色不得修改或删除。

### 7.5 部署拓扑与故障边界

```text
Cloudflare CDN/WAF
    -> 单台 VPS
       -> web：Axum + Askama + 少量 TypeScript
       -> bbbcm-worker：Outbox、媒体、邮件、统计和定时任务
       -> PostgreSQL 16 单主：全部业务事实与事务
       -> Redis 8：缓存、限流、短期协调和唤醒
    -> 外部 S3 兼容对象存储候选：附件与证据（供应商、地域与跨境边界须在 M0 批准）
    -> SMTP、OAuth、Cap.js
```

- PostgreSQL 使用独立持久化卷和 TLS；不配置数据库自动故障切换。数据库故障时写接口返回 `503`，公开缓存内容可短时继续提供。
- Redis 故障不阻断普通阅读；S3 故障时禁止新附件，但纯文本内容继续可用。
- 以 1 万注册用户、300 峰值在线、约 100 万主题与回复，以及 200 read/s、20 write/s 作为容量与压测起点；最终规格由 PostgreSQL 锁等待、WAL、autovacuum、索引和连接池指标确定。
- 匿名列表和公开主题允许 30 秒级边缘或应用缓存。
- 登录页面、个性化页面和私有内容不得串用户缓存。
- 内容哈希静态资源使用一年 `immutable` 缓存。
- 通知、媒体处理和统计失败不能阻塞公开阅读；仅在 PostgreSQL 主库仍可用而全文检索路径故障时，才可回退到经过同等服务端权限过滤的时间流。PostgreSQL 主库故障时只能提供已有的短期公开缓存，不得现场查询或从未授权候选中拼接结果。

## 8. 非功能需求

### 8.1 安全

- 全站 HTTPS、HSTS、严格 Cookie、CSRF、防点击劫持、CSP、`nosniff` 和权限策略。
- 密码使用 Argon2id 或成熟框架安全默认值。
- Markdown 消毒、输出转义、SQL 注入、SSRF、开放重定向和文件上传防护。
- SQL 值一律使用 `sqlx` 绑定参数；schema/table 名只允许由受信标识符渲染器生成，禁止拼接请求输入。PostgreSQL 角色至少区分 `app_rw`、`worker_rw`、`migrator` 和 `report_ro`。
- 图片代理使用来源白名单或签名 URL，并限制响应大小、像素、重定向和超时。
- 登录、注册、邀请、搜索、发帖、回复、私信、反馈和活动分别限速。
- 密钥存入 secrets manager，不进入仓库、客户端包或日志。
- 敏感字段使用 envelope encryption；`bcm_audit.audit_events` 只允许追加，应用角色不得修改或删除。
- 后台高危操作重新认证；所有者、管理员、版主、客服、风控运营和活动运营强制 MFA，商家功能启用后认证商家强制 MFA。
- 生产环境禁止暴露 `9222` 等调试端口；本地调试仅监听 `127.0.0.1` 并使用独立浏览器资料目录。
- 持续进行漏洞、许可证和密钥泄露扫描。
- 统一漏洞严重度和修复 SLA；公开测试前不得存在已知 Critical 或 High。

### 8.2 隐私与数据

- 建立数据清单，区分公开内容、账号数据、私信、认证材料、风控数据、审核证据和安全日志。
- 每类数据定义用途、访问角色、保存期限、删除方式和法律依据。
- 日志不得记录密码、Cookie、令牌、有效邀请码、完整证件、私信正文和兑换码。
- 后台查看敏感资料、搜索用户、导出、权限变更、处罚、认证和积分调整全部审计。
- 分析数据尽量匿名化或伪匿名化；用户删除后按政策去标识。
- 第三方邮件、验证码、分析、对象存储和风控供应商需做数据处理与退出评估。
- 面向中国大陆或其他地区运营前，专项核验备案、内容治理、个人信息、未成年人、跨境、交易和促销规则。
- 应急手册包含数据泄露评估、证据保全以及适用地区的用户和监管通知时限。

### 8.3 性能

- MVP 记录公开缓存读、动态读和写接口各自的实际可用性，不把当前 PostgreSQL 单主拓扑包装成高可用服务；任何对外可用性承诺都必须先明确端点、维护窗口和统计口径，并另行批准主备设计、取得故障切换与恢复证据。
- 常用公开只读接口 p95 不超过 400ms。
- 写接口 p95 不超过 800ms。
- 首屏服务端响应 p95 不超过 800ms，按主要用户地区测量。
- 容量基线为 1 万注册用户、300 峰值在线、约 100 万主题与回复；以 200 read/s、20 write/s 作为压测起点，并在统一硬化阶段固化地区、设备、缓存冷热状态、测量窗口和单 VPS 规格（DEC-020）。
- `pg_jieba` 中文相关性、权限过滤与百万内容重建基准统一在硬化阶段建立并通过（DEC-020）；最终数据库规格由锁等待、WAL、autovacuum、索引与连接池指标确定。
- 首页和版块首屏压缩后 HTML 体积预算在统一硬化阶段按移动网络实测确定（DEC-020）；编辑器、代码高亮、灯箱按需加载。
- 活动峰值按预计日常峰值 3 倍压测，红包领取需单独做并发测试。

### 8.4 可靠性

- PostgreSQL 是结构化业务数据的唯一事实源；Redis 缓存、搜索索引和派生投影必须可由持久事实重建。
- 首发不配置数据库自动故障切换；PostgreSQL 故障时写接口返回 `503`，公开缓存内容可短时继续提供。
- Redis 故障时普通公开读取回源 PostgreSQL，注册、领奖和其他高风险限流操作失败关闭；S3 故障时禁止新附件但纯文本继续可用；通知失败不阻止发帖。
- 仅在 PostgreSQL 主库可用而全文检索路径故障时，搜索才允许回退到经过同等服务端权限过滤的时间流；主库故障时只能提供已有公开缓存，不得使用未授权候选或陈旧缓存放宽可见性。

### 8.5 可观测性

- 技术指标：请求率、错误率、延迟、PostgreSQL 连接池/锁等待/长事务/死锁、autovacuum、表膨胀、Outbox/jobs/DLQ 积压、Redis 缓存命中、PostgreSQL 搜索延迟、邮件失败和对象存储异常。
- 业务指标：注册失败、邀请转化、垃圾帖、举报积压、封禁率、认证积压、积分发行/回收、账本差异、活动预算和领取集中度。
- 高危告警：超级管理员创建、MFA 关闭、批量提权、大额冲正、认证材料批量查看和日志关闭。
- 请求、领域事件和异步任务使用关联 ID，但日志不包含敏感正文。
- 建立账号接管、管理员泄露、积分重复发放、活动超发、数据库损坏、对象存储泄露和垃圾注册的应急预案。

### 8.6 无障碍、国际化与兼容性

- 核心流程达到 WCAG 2.2 AA 基本要求。
- 完整键盘导航、可见焦点、语义标签、正确表单错误和状态提示。
- 不以颜色作为唯一状态信号，交互目标满足移动端可触达尺寸。
- 图片支持替代文本，验证码提供可访问替代方案。
- 所有时间 UTC 存储，按用户时区展示；活动截止明确显示时区。
- 中文简体为默认，可扩展繁体和英文；搜索支持简繁匹配。
- 支持最近两个稳定版 Chrome、Safari、Firefox、Edge 以及主流移动浏览器。

### 8.7 测试策略

执行时机按 DEC-020 分层：开发期每次提交只运行格式化、Clippy `-D warnings`、单元测试、SQLite 冒烟与 `git diff --check` 最小集；下列真实 PostgreSQL 双前缀集成、真实 Redis、双后端矩阵、安全、并发、性能与视觉套件统一在发布前硬化阶段集中执行。

- 单元测试：领域规则、权限、积分、邀请、活动资格和内容转换。
- 集成测试：真实 PostgreSQL/Redis、默认与非默认 schema 前缀、事务回滚、唯一约束、同/异载荷幂等、`If-Match`、死锁/序列化重试、Outbox 租约/重复投递、邮件、搜索、对象存储和 OAuth；SQLite 体验模式另以真实 SQLite（WAL）覆盖注册、登录、发帖、回复、标题搜索、举报和基础后台核心流程。
- E2E：注册、验证、发帖、回复、举报、找回密码、注销、商家和活动核心流程。
- 安全测试：XSS、CSRF、SQL 注入、越权、邀请码枚举、SSRF、上传绕过、重放和限速。
- 并发测试：1,000 路邀请消费、积分结算、投票、悬赏采纳、红包领取和开奖，验证无双花、超发与重复结算。
- 搜索测试：中文相关性、权限过滤、删除传播、百万内容重建和签名游标稳定性。
- Redis 清空或不可用不得丢失业务事实。
- 权限矩阵自动化测试覆盖所有角色、状态和版块范围组合。
- 视觉/E2E 固定覆盖 `1440/1024/768/760/390/320px`、明暗主题、无 JavaScript 核心流程、键盘操作和 WCAG 2.2 AA，并按 `05` 与 `sb.sb` 冻结基准执行品牌资产哈希、计算样式、几何和像素差异校验。

## 9. 发布阶段与里程碑

- 确认一句话定位、目标用户和首发版块。

- 锁定 Rust/Axum/Askama/`sqlx`、PostgreSQL 16、Redis 8 与 `pg_jieba` 运行镜像，批准 `bcm_` schema 前缀、权限模型和迁移规范。
- 批准数据保留矩阵、既定容量与性能负载档案、邮件域和对象存储地域/跨境边界。
- `pg_jieba + pg_trgm` 中文相关性、权限过滤和百万内容重建基准统一在发布前硬化阶段验证（DEC-020），不再作为 M0 退出条件；未通过不得发布搜索。

- 完成规则、隐私、条款、举报和应急手册初稿。

退出条件：没有未决的定位、架构和高风险合规问题。

### 阶段 1：可治理的内容论坛（MVP）

- 账号、邮箱验证、邀请码、特权账号 TOTP 和基础信任等级。
- 版块、主题、回复、不可变内部修订、Markdown、草稿和安全附件。
- 首页、搜索、收藏、关注、通知和阅读状态。
- 举报、审核、处罚、独立申诉、客服工单、紧急请求、规则版本和基础后台。
- PostgreSQL 事务性 Outbox、Worker、主搜索、显式迁移、SSR、SEO、RSS 和数据指标。
- 公开阅读、邀请码注册、邮箱验证后发言，只开放四个首发版块。

退出条件：五条关键 E2E 流程通过，空库迁移、Redis 清空降级和 Outbox 重放完成，无阻断级安全问题。

### 阶段 2：信任与留存（P1-A）

- 普通会员可选 TOTP、Passkey、会话增强和第三方账号。
- 自动化信任重算、不可变积分流水、质量奖励和签到。
- 有效邀请奖励、邀请风控和邀请 cohort 分析。
- 私信、关注用户、通知摘要和个性化阅读。
- 采纳答案、投票、悬赏和树形回复。

退出条件：连续 4 周非活动内容 W1 留存和有效贡献者稳定增长；幂等重放、并发双花、冻结/退款和冲正全部通过。

### 阶段 3：商业供给（P1-B）

- 商家认证、到期复审和公开名录。
- 结构化交易/优惠模板、编辑历史、有效期和 AFF 标识。
- 交易投诉、评价资格和商家数据指标。

退出条件：禁售规则已批准；认证材料保留与删除任务、投诉与暂停认证流程、审核利益冲突和越权测试全部通过；投诉、认证和过期内容均在批准的目标时限处理。

### 阶段 4：可审计活动（P2）

- 活动审批、预算账户、资格风控和审计。
- 抽奖、红包、兑换码、结果公示和冲正。
- 活动榜与内容质量榜分离。
- 只使用不可兑付积分或合规的非现金奖品。
- 商家团队、明确标记且不影响自然排名的赞助位、外部订单只读同步和高级商业指标。
- 可解释的复杂团伙识别、JIT 生产访问、临时提权和完整管理员会话审计。

退出条件：适用地区法律审批留档；预算预冻结、候选快照、随机重放、并发、防刷、取消退款、奖品交付、未领奖与作废流程完成专项测试；高级商业与复杂风控/JIT 分别通过最小权限、敏感访问审计、自动到期和赞助/自然排名隔离验收。高风险功能默认关闭，仅由各能力自己的验收记录解锁。

### 阶段 5：开放生态（P2/Later）

- API、Webhook、机器人账号和外部通知桥接。
- 经授权的跨域内容与数据导入导出。
- 知识库、专题策展和受控 AI 助手。

## 10. MVP 上线验收门槛

本节 18 条均为发布门槛；按 DEC-020 验证分层，统一在功能开发完成后的发布前硬化阶段集中验证，开发期需求与工作包最高标记 `Implemented`，`Verified` 及以上状态只能在硬化阶段凭证据授予。

### 产品与内容

- [ ] 游客阅读、邀请注册、发帖回复、举报处理、账号找回五条主流程在桌面和移动端通过。
- [ ] 问答/实战、AI、域名与主机、站务四个首发版块均已创建；每个版块有规则和种子内容，内容负责人当前待定且必须在公开测试前登记。
- [ ] 冷启动实际到位 3 至 5 名创始成员、2 名稳定答题者、1 名管理员、0 名版主和约 10 篇种子内容；2 名稳定答题者与 1 名管理员完成首周排班并能处理预估峰值。
- [ ] “草莓论坛”品牌标识、品牌资产、明暗主题及首页/版块/主题/注册/登录/发帖/个人页/设置页/后台外壳在六个固定视口通过 `05` 视觉回归门禁。
- [ ] 可计算有效贡献者、首次回复时间、零回复率和非活动留存。

### 权限与安全

- [ ] 所有已实现的 MVP 角色、资源范围和正交内容状态组合通过后端权限测试。
- [ ] XSS、CSRF、越权、邀请码枚举、上传绕过和重复提交有自动化测试。
- [ ] 所有者、管理员、版主、客服、风控运营和活动运营启用 MFA；未启用账号无法获得特权角色。
- [ ] 高风险功能总开关、只读模式、关闭注册和暂停奖励可用并通过测试。

### 治理与合规

- [ ] 服务条款、隐私政策、社区规则、交易风险说明和申诉规则已发布并版本化。
- [ ] 举报、处罚、申诉和证据快照全流程通过。
- [ ] 版主无法查看无关认证资料或修改积分账本。
- [ ] 管理员、版主、客服和用户处罚流程有书面运行手册。

### 数据与运维

- [ ] 搜索、RSS 和站点地图不泄露待审、删除、仅会员内容或有效邀请码。
- [ ] `pg_jieba + pg_trgm` 在百万内容基线通过相关性、权限过滤、删除传播、重建和游标稳定性验收。
- [ ] Redis 清空或不可用时不丢业务事实；Outbox 重复投递不会重复产生外部副作用。
- [ ] 在 1 万注册用户、100 万内容、200 read/s、20 write/s 基线下，公开读 p95 `<=400ms`、写 p95 `<=800ms`、SSR 首屏 p95 `<=800ms`。
- [ ] 隐私导出、账号注销、到期删除和法律保留流程可执行。

## 11. 开发前必须回答的开放问题

下列问题全部保留为 M0 决策入口。标记为“已决”的答案来自 2026-08-30 用户确认；“部分已决”和“未决”项仍须补齐责任人、截止时间与批准证据，详见 [`99-traceability.md`](99-traceability.md) 的决策登记。

1. **已决**：定位为面向独立开发者和海外 IT 从业者的 AI、域名与云基础设施实战社区。
2. **未决**：是否已有博客、Telegram、邮件列表或合作社区作为首批流量来源？
3. **部分已决**：首发版块已固定为问答/实战、AI、域名与主机、站务四个；每个版块的内容负责人仍待确定。
4. **部分已决**：在已确定的 PostgreSQL 单主和单 VPS 拓扑下，生产实例规格、独立持久化卷、连接池和扩容阈值如何配置？
5. **已决**：最终注册策略为公开阅读、邀请码注册、邮箱验证后发言；邀请默认每日 5 个、未使用最多保留 5 个，并按信任等级调整。
6. **部分已决**：目标用户为中国大陆及跨境中文用户；主要运营主体以及适用的备案、内容和数据要求仍待确认。
7. **部分已决**：平台只提供交易信息，不托管资金、不担保履约；允许品类和禁售清单仍待批准。
8. **部分已决**：商家核验范围、`/manage` 人工审核和一年复审已确定；材料保存期限、具体审核责任人仍待确认。
9. **已决**：积分永久不可提现、不可兑法币、不可自由转让；打赏和悬赏只允许受约束业务结算。
10. **部分已决**：抽奖参与成本为 0，积分不可兑付；是否启用实物或高价值奖品仍待确认。
11. **未决**：邮件、对象存储、验证码和错误追踪选用哪些供应商，`pg_jieba` 词典与相关性基准由谁维护？
12. **部分已决**：冷启动由管理员承担审核与治理；申诉、诈骗投诉、安全事件和灾难恢复的最终责任人仍待确认。
13. **部分已决**：最小拓扑为 Cloudflare 前置和一台 VPS；VPS 规格、月度金额、资源配额和扩容条件仍待确认。
14. **未决**：哪些指标达到后才允许进入商家、积分和活动阶段？
15. **已决**：项目名称为“草莓社区”；视觉风格与品牌标识严格复制 `sb.sb`，公开页头品牌文案使用“草莓论坛”，详细基准和差异门禁见 `05`。

## 12. 完成定义（Definition of Done）

任何功能只有同时满足以下条件才算完成；按 DEC-020 验证分层，下列条件中的真实 PostgreSQL 双前缀迁移、集成与 E2E、安全、无障碍和视觉等重型验证统一在发布前硬化阶段集中执行，开发期每次提交只运行格式化、Clippy `-D warnings`、单元测试、SQLite 冒烟与 `git diff --check` 最小集，需求与工作包最高标记 `Implemented`，`Verified` 及以上状态只能在硬化阶段凭证据授予：

- 产品需求、空状态、错误状态、权限和边界条件明确。
- 前后端均做服务端权限和输入校验。
- 数据迁移、索引、日志和指标已实现。
- 核心写入的不变量、幂等、实体版本和 Outbox 已在同一 PostgreSQL 事务验证。
- 迁移在默认与非默认 schema 前缀的真实 PostgreSQL 通过；Handler 不直接写 SQL，查询值无字符串拼接。
- 单元、集成和关键 E2E 测试通过。
- 桌面、移动、键盘和基本无障碍验证通过。
- 安全与隐私影响已评审，敏感数据不会进入日志。
- 运维文档和故障降级已准备。
- 用户帮助、规则或管理手册同步更新。
- 功能开关、灰度策略和退出条件已明确。
