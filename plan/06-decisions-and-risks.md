### `DEC-062` MFA 密钥存储与新增加密依赖（2026-09-06 批准）

`AUTH-011`／`AUTH-012` 要求特权角色强制 TOTP。TOTP 是对称算法，共享密钥必须可逆存储才能验签，因此「只存哈希」不适用于它（`03` §6 的只存哈希规则适用于恢复码，本条不改动）。项目所有者批准：

- **加密存储**：共享密钥用 AEAD 加密后落库，库中只保存密文、nonce 与密钥版本；明文只在绑定与验签的内存过程中存在，不进日志、错误响应、Outbox 或审计详情，`/manage` 永不返回（C3）。
- **包裹密钥**：沿用 `DEC-051` 的版本化外部 Secret keyring 与用途隔离派生，MFA 用途与邮件、风险密钥相互隔离；轮换通过注入新版本并保留旧版本完成，旧版本仅用于解出既有凭据，退役条件与 `DEC-051` 一致。
- **新增依赖**：引入 `chacha20poly1305`（AEAD）与 `sha1`（RFC 6238 默认算法，主流认证器普遍只支持 SHA-1）。两者均属 RustCrypto 同族，与既有 `hmac`／`sha2`／`argon2` 维护方一致。按 `WP-M0-03` 的规则，传递依赖以根 `Cargo.lock` 为准，registry 包数由 326 增至 335；`supply-chain/README.md` 的登记值同步更新。
- **恢复码不变**：只存哈希、只显示一次、单次消费，按 `03` §6 执行。

数据库泄露不再等同于全部特权账号 MFA 失效，这是选择加密存储而非明文加 ACL 的直接原因。真实密钥来源、轮换运维与生产 KMS 仍属 `DEC-011`／`DEC-059`；未注入 MFA keyring 时绑定与验签一律失败关闭，不退化为明文存储。

### `DEC-063` Redis 合同运行时只锁大版本（2026-09-07 批准）

`WP-MVP-E01` 首次执行真实 Redis 合同时，本机 `redis-server` 为 8.8.0，而 `supply-chain/lock.json` 锁定的镜像基线是 8.2.9-bookworm，`99` 第 5.23 节据此把该结果登记为「不能充当锁定基线证据」。项目所有者批准调整口径：

- **合同运行时只锁大版本**：真实 Redis 合同要求运行 Redis **8.x** 即可，不再要求与供应链锁定镜像的小版本一致。测试内已有的 `redis_version:8.` 断言就是这条要求的完整实现，不需要加严。
- **理由**：合同验证的是 Redis 8 的命令与 Lua 原子性语义（`SET NX PX`、单键 Lua CAS、`XADD MAXLEN`/`XREAD BLOCK`、`SCAN`+`UNLINK`），这些在 8.x 补丁线内没有语义差异；把证据绑定到单个补丁号只会让证据随上游发版失效，并不增加保障。
- **供应链镜像锁不变**：`supply-chain/lock.json` 的 `images.redis` 仍保留精确 tag、index/平台摘要与 `REDIS_VERSION`，`scripts/supply-chain.py` 的 `8.\d+.\d+-bookworm` 校验也不放宽。镜像摘要锁服务的是**可复现构建与 SBOM 溯源**，与合同测试跑在哪个 8.x 服务端上是两件事，本决策不触碰它。
- **影响**：`99` 第 5.23 节的偏差登记与第 3 项残留阻塞项一并解除；已执行的 8.8.0 合同结果按正式结果计入 E01 的 Redis 一项。它仍**不使任何需求进入 `Verified`**——`DEC-020` 要求完整矩阵，Redis 只是其中一项。

### `DEC-064` 内容写路径不再锁版块行（2026-09-07 批准，修订 `DEC-052` 锁序）

`WP-MVP-E01` 在真实 PostgreSQL 上执行内容写入时暴露一处**事实源互相冲突**，两条都写在计划里，但在 PostgreSQL 上不可能同时成立：

| 事实源 | 内容 |
|---|---|
| `02` 第 386 节、`DEC-052` | 写锁序为 幂等 → `identity.users` → `identity.sessions` → `trust.identity_snapshots` → `community.commit_state` → **`forums`** → `topics` → `posts` |
| `db/migrations/postgres/0001_init.sql:120` | 运行角色对 `community.forums` 只有 `GRANT SELECT` |

PostgreSQL 的 `SELECT … FOR UPDATE` 需要 `UPDATE` 或 `DELETE` 权限，只有 `SELECT` 会直接报 `permission denied for table forums`。后果是**完整模式下建主题、回复、编辑、删除、移帖全部失败**，且不限于并发，单请求也必然失败。SQLite 侧看不到：`lock_sql` 对 SQLite 返回不带 `FOR UPDATE` 的原始 SELECT，SQLite 也没有表级授权。

项目所有者批准的解决方向：**去掉版块行锁**，保留 ACL 不变。

- **锁序修订**：新的写锁序为 幂等 → `identity.users` → `identity.sessions` → `trust.identity_snapshots` → `community.commit_state` → `topics` → `posts`，`forums` 不再参与加锁。`02` 第 386 节同步改写。
- **为什么安全**：版块是迁移/种子维护的参照数据，运行角色本就没有写权限，运行期不存在并发改写；而 `community.commit_state` 根锁已经把所有社区写串行化，版块行锁不提供额外互斥。
- **保留的部分**：版块链的校验（可见性、`status = 'active'`、父链环检测）**全部保留**，只是不再对链上每个版块取行锁。函数据此更名，避免一个叫 `lock_forum` 的函数实际不加锁。
- **最小权限不放宽**：`community.forums` 的 `GRANT SELECT` 保持原样，`app_role_cannot_write_reference_tables_but_can_read_them` 断言继续成立，不做任何修改。

被否决的替代方案：给 `app_rw` 增授 `forums` 的 `UPDATE`。它改动最小，但会让运行角色获得改写参照数据的能力，削弱最小权限，并与上述断言直接冲突。

### `DEC-065` 纯 ACL 迁移的 N 轨配对形式（2026-09-07 批准）

`WP-MVP-E01` 发现 `0016_iam.sql` 漏授 `GRANT USAGE ON SCHEMA iam`，导致完整模式下整个 `/manage` 不可用。修复本身无争议，但迁移不可改历史文件，必须新增前向迁移，而这类**纯 ACL 修复在 SQLite 轨没有任何对应语句**——SQLite 没有 schema 级权限概念。既有规则同时要求：编号集合跨 postgres／sqlite 完全一致（`verify_alignment`），且每个迁移至少含一条可执行 SQL（`validate_content`）。两条一起把纯 ACL 修复堵死了。

项目所有者批准放宽，并要求补一条防滥用约束。落地形式如下：

- **文件仍然配对存在**，编号集合保持完全一致。放宽的是 `validate_content`：当且仅当文件首行为声明标记 `-- BBBCM-TRACK-NOOP:` 时，允许它不含可执行 SQL，标记后必须写明该轨为何无事可做。
- **为什么不是「某一轨缺号」**：批准意见要求「缺号必须是纯 ACL」的约束可被检查，而文件不存在时无从检查任何东西。保留文件并要求显式标记，既不往 SQLite 轨塞占位语句（这正是要避免的），又让约束真正可被机器挡住，同时 `git log` 里能看到这条迁移在每一轨的意图。
- **适用范围限定**：标记只用于「该轨确实无对应语义」的迁移，典型是 PostgreSQL 专有的 ACL。不得用它跳过本应实现的 schema 变更——那会让两轨结构悄悄分叉。
- MySQL 8.0 轨仍整轨为空，规则不变。

同步 `02` 迁移规范一节。

### `DEC-066` 举报合并加序列化点（2026-09-07 批准，扩展 `DEC-052`／`DEC-064` 锁序）

`WP-MVP-E01` 的并发载体发现：8 路并发举报同一目标会开出 8 个案件。`case_repo::open_case` 是不带 `FOR UPDATE` 的普通 `SELECT`，`submit_report` 读到 `None` 即建案，而 `case_target_idx` 是普通索引不是唯一索引——没有任何序列化点，`MOD-002` 的合并语义在真实并发下不成立。

项目所有者批准**加序列化点**，而不是加唯一偏索引：

- **理由**：唯一偏索引语义更贴切，但 MySQL 8.0 不支持偏索引，与 `DEC-022` 的三库交集子集直接冲突；加锁不受该限制，MySQL 接入时同样可用。
- **实现**：在 `submit_report` 读取既有案件**之前**，按 `(target_kind, target_id)` 取一把事务级顾问锁。PostgreSQL 用 `pg_advisory_xact_lock`，键由应用侧稳定哈希算出并以 bind 参数传入（不用 `hashtext`，它不保证跨版本稳定）；SQLite 为单写者，天然串行，该处为 no-op。
- **锁序**：`moderation` 的这把锁排在 `community` 之后、追加段之前。`02` 第 386 节同步补写。它是顾问锁不是行锁，不与既有行锁争用，但仍纳入冻结总序以免后续有人在它之后再补取更早的领域锁。

项目所有者提交了一份新的社区定位，与既有事实源在三处冲突。三点均已裁决，本条是登记出处。

**（一）首发版块由四个替换为六个。** 原「问答/实战、AI、域名与主机、站务」整体作废，改为：

| 名称 | slug | 一句话描述 |
|---|---|---|
| 日常 | `daily` | 生活闲聊、职场吐槽、杂谈与轻度交流。 |
| 酷品 | `showcase` | 秀出你的作品、新奇玩具与实战项目。 |
| AI | `ai` | 探讨前沿大模型、AI 生产力与工程化落地。 |
| 主机 | `hosting` | VPS、云计算、网络路由与服务器基础设施。 |
| 版本 | `releases` | 本社区项目发版动态与官方更新日志。 |
| 站务 | `meta` | 关于本站的建议、Bug 反馈与社区公告。 |

只有 `ai` 的 slug 原样保留，其余四个是改名兼改 slug，并净增两个。原「域名与主机」的域名部分并入「主机」；原「问答/实战」的实战复盘部分并入「酷品」，日常求助并入「日常」。`CAT-000` 关于「交易与优惠」须待 P1-B 商业安全门槛的限制不变，六个版块中没有交易类版块。

**（二）版块页路由由 `/c/{slug}` 改为顶级 `/{slug}`。** `01` 第 10 节原写 `/c/{slug}`，实现写的是 `/forums/{slug}`，两者本就不一致；本次统一取顶级形式，两个旧形式都作废。按 `AGENTS.md`「不为未发布实现保留兼容分支」，`/forums/{slug}` 不做 301，直接替换。

顶级 slug 与站点级静态路由共用同一段命名空间，因此附带一条**保留字约束**：版块 slug 不得取用任何已注册的顶级静态路径段。路由匹配上静态段优先于参数段，冲突不会表现为 500，而是该版块**永远无法访问**——这种失败没有报错，必须在建号时挡住，不能靠上线后发现。保留字清单与校验点写入 `02`，由种子与将来的建版块入口共同强制。

**（三）导航条目由四项增至六项，不登记为 A00 冻结例外。** 项目所有者明确「不是例外，按六个导航修改现在的文档」，因此 `05` 第 10 节的具名例外条目由「四个自定版块名称」改写为「六个」，冻结基准本身按六项更新，而不是在冻结之上挂一条豁免。模板改动限于导航与移动版块条的条目文字和链接，不新增结构层级、不改 CSS 类名，`DEC-021` 冻结的其余范围不变。

### `DEC-067` 无障碍叠加层（2026-09-07 批准，部分实测否决）

`WP-MVP-E01` 的浏览器结构化检查发现两条事实源在当前参考标的上不可兼得：`05` 第 6 节与 `90` 第 5 节要求触控目标 ≥44px、对比度达 WCAG 2.2 AA；而 `05` + `DEC-021`／`DEC-046` 要求严格复制 `sb.sb` 公开视觉风格、不得降级为近似设计，A00 模板与 CSS 已冻结。

项目所有者批准「叠加无障碍层」：保持参考设计可见外观，另加一层只改可访问性的补丁。执行后两半结果不同，如实登记：

- **对比度：已实施并全量达标**。新增 `apps/web/static/css/a11y.css`，在三份参考样式之后加载。取值由实测求解——沿明度轴向背景反方向移动，取第一个达到 4.5:1 的颜色，保留原色相与饱和度，使偏离最小。共五处：`.topic-pinned .post-title`、`.footer-version`（明暗各一）、`.post-user-group`、`.post-user-group--staff` 背景。14 页 × 两视口 × 两主题复测失败项为 0。这五处构成 `05` 第 10 节像素基准的**已登记例外**。
- **触控热区：实测否决，未采用**。原计划用 `::after` 覆盖层撑到 44px 而不动可见尺寸，实测显示：390px 视口下 8 类受控元素的 68 个实例中有 **54 个**扩大后与相邻目标重叠——点击归属不确定比目标偏小更糟；且规模远超批准时的前提，同视口 559 个非内联交互目标中有 **505 个**低于 44px，逐个加热区等于给整个列表铺满互相重叠的判定区。

**触控目标门槛因此仍待裁决**，并需注意两条要求的量级差异：`05` §6 写的 44px 相当于 WCAG 2.5.5（AAA）与移动 HIG；而 `90` §5 要求的 WCAG 2.2 **AA** 对应 2.5.8「目标尺寸（最小）」的 **24×24**，且允许用间距替代。按 AA 口径硬性不达标的是 192 个而非 505 个。实测数据见 `docs/evidence/mvp/wp-mvp-e04/dev-20260907/`。

模板改动仅为每份模板增加一行 `<link>`，未改结构与类名，符合 `DEC-021` 冻结的既定范围。

### `DEC-055` Unicode 折算与自然周起点（2026-09-06 批准，补齐 `DEC-049`）

项目所有者（用户）批准：字符计量按 Unicode 标量，1 标量 = 1 字符，中日韩字符不做宽度折算；自然周按 ISO-8601 从周一 00:00 UTC 开始。`DEC-049` 遗留的两项计算分支自此解除等待，长度校验与 WAU/MAU、果农指数窗口可按此实现。同步 `01` §1.3、`DATA-002`、`02` §17。批准口径不等于统计已实现。

### `DEC-056` 移帖跳转语义（2026-09-06 批准，关闭 `CR-012`／`DEC-017`）

项目所有者（用户）批准：移动主题＝同一对象更换 `category_id`，主题 ID、楼层与回复全部不变，不克隆、不新建 ID、不建别名表。权威永久链接定义为 `/t/{id}`，不含版块段；任何含版块段或旧 slug 的历史 URL 一律 301 到当前规范 URL。`CAT-014` 自此解除 `Blocked`，`CR-012` 的 ID 冲突不再存在。管理员移动操作仍须审计，版块权限按 `CAT-015` 同步作用于列表、搜索、RSS、站点地图与分享摘要。

### `DEC-057` 视觉基准冻结（2026-09-06 批准，关闭 `DEC-019`）

项目所有者（用户）批准：立即以 `WP-MVP-A00` 已交付产物冻结 `visual-baseline-v1`——14 个隔离 SSR 夹具、30 项本地源资产与「草莓论坛」品牌文案构成实现基准，参考站公开截图继续承担几何比对角色，即 `05` 第 2 节的两部分组合方式获批。`WP-M0-02` 与 `05` 第 14 节的两项 M0 交付物自此可完成，`05` §15 的像素与几何门槛获得参照。

冻结不等于门禁通过：`05` §15 全部条目仍在统一硬化阶段（`WP-MVP-E04`）用固定浏览器、字体、缩放、视口与主题重拍验证（`DEC-020`）。后续真实页面只能在本基准上演进，不得另起一套基准；确需变更基准时按本文件第 5 节流程重新批准并记版本号。

### `DEC-058` 权限 registry 与 SiteOwner 权限集（2026-09-06 批准，关闭 `CR-011`／`CR-013`／`DEC-016`／`DEC-018`）

项目所有者（用户）批准：

- 仓库内单一 TOML registry 文件是角色、权限、配置键的唯一事实源；构建期由它生成 Rust 枚举与数据库种子，三者不一致时启动拒绝。不得建立多套同义角色，不得手写与 registry 并行的权限常量。
- SiteOwner 权限集固定为四类极高危运维：密钥轮换、账单与供应商、生产访问授权、灾备恢复。不含任何内容、用户、审核或客服日常权限，禁止用 `all permissions` 通配代替，也不包含紧急内容下架。

`/manage` 的 `D01`–`D04` 与生产 IAM provisioning 自此解除决策阻塞；实际实现、审批链与审计接线仍属对应工作包，本条不授予任何实现状态。`03` 第 3 节的最低边界继续全部有效。

### `DEC-059` 外部 provider 选型方向（2026-09-06，部分批准）

项目所有者（用户）批准 `DEC-011` 的方向为**托管服务优先**：邮件投递、对象存储、验证码、错误追踪优先采用托管 SaaS，而非单 VPS 自建。方向获批不等于选定供应商——具体厂商、区域、合同、隐私评估与费用仍 Pending，依赖 `DEC-013` 预算与 `DEC-006-B` 法律主体。

未选定前维持既有未决行为：只交付 adapter、故障语义、配置开关与本地测试实现，真实接入保持关闭，按 `README` 第 6 节可记 `Implemented`。密码泄露语料继续按 `DEC-051`／`CR-014` 使用本地版本化离线摘要，不因本条转为在线服务；搜索词典 `pg_jieba` 属自建扩展，不在托管方向范围内。
