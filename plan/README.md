## 1. 计划目标

以可审计、可恢复、可逐步开放的方式建设“草莓社区”：

- 中文项目名：草莓社区。
- 页头品牌文字：草莓论坛。
- 英文代码名：`bbbcm`。
- 数据库 schema 前缀：`bcm_`（PostgreSQL；SQLite 为扁平表名）。
- 积分昵称：草莓。
- 核心指标：果农指数。
- 公开视觉严格复制 `sb.sb` 可公开观察的视觉语言与品牌标识，不热链资源；开发第一步先做参考标的本地化（`WP-MVP-A00`，`DEC-021`），本轮采集与资产登记顺序按 `DEC-046` 执行。
- 开源双部署形态：PostgreSQL 完整模式与 SQLite 体验模式（降级边界见 `02` 第 6 节），Redis 可选。
- 后续支持 MySQL 8.0：SQL 按 PostgreSQL/SQLite/MySQL 8.0 三库交集编写（`DEC-022`），现在不实现。
- 第一阶段只交付 M0 和 MVP；P1-A、P1-B、P2、P2/Later、Later 能力只能建设关闭状态下的必要底座。

## 5. 两层就绪定义

### Repository Ready

仓库内可独立复核：代码、配置、迁移、默认与非默认 schema、静态检查、单元、集成、E2E、安全、并发、性能夹具、无障碍和实现侧视觉验证均通过。

### Production Approved

需要真实环境或责任人确认：供应商、费用、法律主体、生产规格、冷启动人员和内容、正式视觉基准及 go/no-go 审批均完成。

`Repository Ready` 不能替代 `Production Approved`。生产外部事项未完成时，可以形成发布候选，但不得标记 `Released`。

状态授予按 `DEC-020` 分层：开发期只执行最小验证集，需求与工作包最高标记 `Implemented`；`Verified` 及以上状态只在统一硬化阶段凭证据授予。

## 6. 状态模型

| 状态 | 定义 |
|---|---|
| `Not started` | 尚无交付物 |
| `In progress` | 已开始，但需求仍有明确缺口 |
| `Implemented` | 整条需求的代码、配置或运行手册已经交付 |
| `Verified` | 需求全部验收条件有当前版本的可复核证据 |
| `Release candidate` | 所属阶段的 Repository Ready 门禁全部通过 |
| `Released` | Production Approved、Feature Flag 和观察期均完成 |
| `Blocked` | 唯一剩余动作依赖明确的外部决定或权限 |

禁止把“已有数据结构”“已有接口骨架”“部分路径可用”标记为 `Implemented`。

判定补充（`Blocked` 与外部依赖）：

- 外部 provider 依赖类需求，若 adapter、故障语义、配置开关与本地测试实现均已交付，且能力按已批准的未决行为保持关闭，可记 `Implemented`；真实接入属 Production Approved。
- 行为完全由某条待决决策定义的需求记 `Blocked`，不得记 `Implemented`；对应决策批准后转 `In progress`，实现完成才可 `Implemented`（`CAT-014` 已随 `DEC-056` 完成此转换）。受阻清单见 [`99-traceability.md`](99-traceability.md) 第 4.1 节。

注记（`DEC-020`）：开发期需求与工作包最高标记 `Implemented`；`Verified` 及以上状态只能在功能开发完成后的统一硬化阶段凭证据授予。

## 7. 执行规则

1. 从 `99` 选择工作包和精确需求 ID。
2. 实施前补齐依赖、接口、数据、权限、事务、Outbox、测试和开关设计。
3. 每个工作包形成纵向可运行切片，不以脚手架或文档代替功能。
4. 验证分两层执行（`DEC-020`）。开发期每次提交只执行最小集：格式化、Clippy `-D warnings`、单元测试、SQLite 冒烟、`git diff --check` 与暂存区复核。
5. 完整验证矩阵在功能开发完成后的统一硬化阶段集中执行：真实 PostgreSQL 16 双前缀（默认 `bcm_` 与随机非默认前缀）集成、真实 Redis 8 合同、双后端矩阵、浏览器视觉验证、安全、并发、性能与容量基线。
6. Redis 只保存可丢失、可重建状态并做命名空间隔离，不得作为业务事实源；此类设计纪律不随验证后置放松。
7. 页面浏览器验证（桌面、移动、明暗主题、键盘、无 JavaScript、错误态和视觉差异）归入硬化阶段完整矩阵；开发期页面工作以 `WP-MVP-A00` 冻结的模板、CSS 类名和静态夹具为准。
8. 证据齐全后才更新状态和复选框；证据要求按阶段分层——开发期最小集证据支撑 `Implemented`，`Verified` 及以上须凭硬化阶段完整矩阵证据授予。失败必须保留并修复根因。
9. 每个检查点只提交相关文件，使用中文提交信息，不 push、不部署、不使用真实密钥。
