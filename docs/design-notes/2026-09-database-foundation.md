### 2.1 受信注册与对象命名

`platform::identifiers::SchemaRenderer` 是应用物理标识符唯一生成入口，分别验证已登记 schema、完整 `(schema, table)` 对、受信角色后缀及所需序列/索引对象。仅字符合法的未登记表同样拒绝，例如 `community.users` 或 `platform.anything`。注册不得从请求、配置文件或扫描数据库自动扩充。

本轮仅注册三张初始表及它们实际使用的数据库对象；SQLite 重建替代表名由已注册表派生固定 `_rebuild` 后缀并做长度校验，临时替代表不成为第四张初始业务表。identity.users、platform.outbox_events、audit.audit_events 等未来表不因产品模型中出现而提前获得运行注册或 ACL。新增表的同一次提交必须一起交付注册、两轨迁移、必要索引、显式表/序列 ACL、设计映射与测试。迁移模板中的物理名也经同一个 renderer 生成，禁止硬编码 `bcm_` 绕过非默认前缀。

SQL 值全部 bind。系统目录、PRAGMA、DDL 和角色/锁语句只在受控平台迁移或方言层执行；它们不是业务 Repository 借口。Repository 不持有连接池，不提交事务，Handler 不导入 sqlx 或写 SQL（02 §2.1、§6.1、§9）。

## 3. 本轮三张初始表与种子

精确列名、数据类型和索引名以 `db/migrations/{postgres,sqlite}/` 版本化迁移及受信注册为可执行映射；本节固定其最小语义与约束，不创建平行 Schema 定义。

| 表 | 必要字段语义与约束 | 生命周期 |
|---|---|---|
| platform.schema_migrations | 唯一迁移编号、名称、源文件内容 SHA-256、执行状态、执行时间；编号对应单一源内容，状态以 CHECK 和应用白名单限制 | 由迁移连接管理；已应用记录不得被重写为另一内容，不设自动过期 |
| community.forums | 数据库自增正整数 ID、稳定唯一 slug、名称、骨架状态、确定排序与实体版本 | 四个 development/test 骨架；不创建发帖、权限、层级和内容服务 |
| moderation.rule_versions | 数据库自增正整数 ID、forum_id、版本、占位内容及占位状态；(forum_id, version) 组合唯一，forum_id 外键 RESTRICT | 每版块一个明确的开发占位版本，不冒称已批准规则或政策 |

本轮 forums 先于 rule_versions 插入；规则引用版块，删除版块不能级联破坏规则历史。后续真实规则不可静默覆写旧版本，规则审批、引用、发布和内容业务由各领域工作包完成。当前不引入 forums 指向“当前规则”的反向外键或循环插入依赖。

主键映射遵守 02 §6.2：PostgreSQL BIGINT IDENTITY，SQLite INTEGER PRIMARY KEY AUTOINCREMENT，避免 rowid 复用。种子通过稳定 slug 和 (forum_id, version)回查 ID，不依赖 RETURNING、不显式写死自增 ID、不使用 MAX()+1。时间通过 `platform::db` 编解码，SQLite 时间列为 TEXT NOT NULL、UTC 固定 27 字节 RFC3339 微秒格式；JSON 若以后需要则使用经应用校验的 TEXT，状态以文本与 CHECK 表达。

`bbbcm-cli db seed` 只允许 development/test，必须在连接或写入前拒绝 staging/production。一次种子执行使用专用连接和单个写事务；SQLite BEGIN IMMEDIATE，PostgreSQL 使用包含当前前缀的迁移/种子串行化锁并在锁内检查。先读稳定键，缺失才 INSERT，存在则保留原记录；重复运行不更新已有名称、说明、规则内容、版本或时间。唯一冲突不得让 PostgreSQL aborted 事务继续运行：竞争必须由锁内重查消解，不能写捕获冲突后直接 UPDATE 的路径。

四个名称严格为“问答/实战”“AI”“域名与主机”“站务”。种子不产生用户、员工、SiteOwner、权限 registry、主题或生产 IAM，不启用任何 Flag。它不是 CAT-000/001 的完整产品交付，不替代真实负责人、约 10 篇冷启动内容或已批准政策。初始化无业务事件或外部副作用，因此不伪造 Outbox 和业务审计事件。

## 4. PostgreSQL 数据库角色与 ACL

依据 02 §8，角色使用受信前缀加固定后缀：`<prefix>migrator`、`<prefix>app_rw`、`<prefix>worker_rw`、`<prefix>report_ro`。四者均为 NOLOGIN 组角色，runtime 组同时 NOINHERIT；不得带 SUPERUSER、CREATEDB、CREATEROLE、REPLICATION、BYPASSRLS 等额外权限。密码和真实登录账号不写入仓库。

权限管理员通过单独、版本化的 bootstrap SQL 模板创建/核对角色及所需数据库级权限。该步骤明确要求具备相应权限的管理员执行，迁移命令不得自动越权、创建高权限登录或授予自身角色。受控迁移登录仅获 migrator 的显式 SET ROLE 能力，连接后切换到 `<prefix>migrator`，schema 与表的 owner 因此统一为 migrator。服务登录分别使用其 runtime 组；不得获 migrator 成员身份，不能通过继承或 SET ROLE 逃离 runtime policy。现有同名但属性、所有权或成员关系不符合约束的角色必须停止并由管理员核查，不能把其存在当作安全证明。

### 4.1 初始对象授权矩阵

“无”表示无对象授权；不会因为角色名称包含 rw 就获得写权。

| 对象 | migrator | app_rw | worker_rw | report_ro |
|---|---|---|---|---|
| 15 个应用 schema | owner；执行迁移 | 仅 community、moderation 的 USAGE；无 CREATE | 无 | 无 |
| platform.schema_migrations | owner；读写迁移状态 | 无 | 无 | 无 |
| community.forums | owner；迁移/开发种子 | SELECT | 无 | 无 |
| moderation.rule_versions | owner；迁移/开发种子 | SELECT | 无 | 无 |
| 两张自增表的序列 | owner；种子取值 | 无 | 无 | 无 |
| audit、iam、analytics 中未来对象 | 由对应新增迁移管理 | 默认无 | 默认无 | 默认无 |

新建表和序列在同一迁移中显式撤销 PUBLIC/runtime 的默认授予，再按表中 policy 授予允许权限。默认 ACL 针对实际对象 owner migrator 设置：未来 TABLES/SEQUENCES 不自动授予 PUBLIC 或 runtime；函数的 PUBLIC 默认 EXECUTE 也不得成为未来权限缺口，但应用本身仍按 DEC-022/033 禁止自定义存储过程、触发器、视图。不能用 `GRANT ... ON ALL TABLES` 覆盖后续对象，不能依赖 public search_path 或未检查的权限继承。

应用 schema 对 PUBLIC 无 CREATE/USAGE；runtime 无应用 schema CREATE。管理员 bootstrap 还应检查服务登录在数据库、public schema 与其他成员角色中的创建能力，应用运行账号不得从这些路径取得额外 DDL 权限；共用数据库的全局权限调整必须由管理员按其既有隔离策略处理，runner 不擅自修改其他应用对象。临时 FTS5 探测仅适用 SQLite，不构成放宽 PostgreSQL schema CREATE 的理由。

### 4.2 后续表必须继续满足的策略

- A04 新增审计表时：允许应用命令在业务事务内追加审计，敏感读取在短事务内追加访问记录；app/worker/report 均无审计 UPDATE、DELETE、TRUNCATE，也不拥有审计对象。审计查询只向必要角色开放必要字段；独立权限域副本通过已提交事件复制，不以异步复制替代本地原子审计。
- IAM catalogue 对运行角色只读；授权状态写入由受控命令及专用权限执行，不以 app_rw 全表 UPDATE 实现角色管理。精确 registry 与生产授权仍等待 DEC-016/018、CR-013。
- worker 只获当前 sink/作业所需表与列，新增 sink 同步 policy。report 只读明确脱敏的分析列；analytics schema 存在本身不赋予任意 SELECT，不能把 audit 或其他 C2/C3 原始数据作为报表捷径。
- 真实 PostgreSQL 中由 migrator 创建未来表/序列探针，并检查 owner、PUBLIC、成员继承、SET ROLE 与默认 ACL，属于 E01 的完整验证。本轮交付 SQL 与静态/设计检查，不冒称已运行真实权限矩阵。

SQLite 无数据库角色和列级 ACL，体验模式依赖本机文件权限与应用边界；不得用一张“角色表”伪造 PostgreSQL 的权限保证。MySQL 8.0 不接入，账号模型后续另定。

## 5. 迁移发现、元数据和执行流程

### 5.1 发现与预检查

1. 发现 PostgreSQL/SQLite 两条有序迁移轨，mysql8 仅占位。文件名必须符合 runner 规定的编号与名称格式，同轨编号唯一，两个有效后端编号集合一致。单轨为空、两条有效轨均无迁移、非法编号、非法文件或不一致集合均拒绝，不能继承旧实现“所有空轨豁免”的行为。
2. 迁移源使用 UTF-8、LF、末尾换行，具有实际可执行内容。对完整源字节计算 SHA-256，包含重建标记和模板内容；运行时替换前缀不会改变迁移源的版本身份。模板参数只能引用受信 schema/table/role 等对象，不提供通用字符串插值。
3. 执行前读取完整本轨历史，验证编号、名称、checksum 和状态；已应用但文件缺失、改名、内容漂移、非法状态或不符合顺序的历史均明确拒绝。幂等检查在获得写锁后重做，不能只依赖锁外 status 快照。
4. 正常重复运行报告已有版本并跳过其 SQL，不重复应用。任何修正已应用迁移的需求通过新增编号前向迁移完成，不删除、回写或“修复”checksum。

### 5.2 专用连接与首次初始化

迁移使用 sqlx 专用单连接，不向业务连接池借连接，不使用默认 `_sqlx_migrations`。PostgreSQL 以受控 migrator 角色执行；SQLite 配置 WAL、busy_timeout=5000ms、foreign_keys=ON。迁移元数据物理名经 SchemaRenderer 渲染，与前缀隔离。

首次创建 platform schema 和元数据表同样在受保护的初始化事务中完成，不能为创建锁表而形成“尚无表就无锁”的窗口。PostgreSQL 的前缀 advisory transaction lock 与 SQLite 的 BEGIN IMMEDIATE 在元数据表出现前就可串行化初始化；已有对象必须核对其预期结构和元数据来源，不用 IF NOT EXISTS 静默接管未知同名业务表。

### 5.3 每个迁移的原子边界

| 步骤 | PostgreSQL | SQLite |
|---|---|---|
| 开始 | 专用连接 BEGIN；调用 `pg_advisory_xact_lock(hashtext(?))`，bind 前缀；锁随事务结束自动释放 | 普通迁移 BEGIN IMMEDIATE；重建迁移先在事务外 foreign_keys=OFF，再 BEGIN IMMEDIATE |
| 锁内检查 | 重新读取迁移元数据，检查已应用版本与 checksum | 同左；写锁保证同文件并发迁移串行 |
| 执行 | 受信渲染后执行 DDL/DML 与本迁移显式 ACL | 受信渲染后执行该轨 SQL；不执行 PostgreSQL 角色语句 |
| 提交前 | 同事务登记已应用状态、内容身份与时间 | 重建型在事务内运行 foreign_key_check，任何违规拒绝；同事务登记已应用状态与时间 |
| 结束 | COMMIT，锁自动释放；响应仅在提交明确后成功 | COMMIT 或 ROLLBACK 后恢复 foreign_keys=ON，并确认恢复 |

SQLite `-- rebuild` 必须位于文件头，不能通过任意 SQL 内部自行切换 PRAGMA 或事务。重建迁移流程为创建替代表→复制/转换→移除旧表→替代表改名→重建约束/索引→foreign_key_check，具体数据转换在该迁移逐项说明；禁止不经数据复制和约束检查直接丢表。此处是 runner 支持与合成测试，不表示本轮需要无目的地重建初始表。

### 5.4 状态、失败与恢复

迁移至少区分 pending、applied 与 failed 的执行语义，具体元数据状态值由迁移定义；pending 可由版本集合与历史差计算，不要求为未执行版本提前写行。执行中信息不能提前被当成已应用。成功状态和 DDL/DML 必须同事务提交，因此不会出现结构失败但元数据声称成功。

可确定失败先完整回滚本迁移；已成功的较早迁移保留。退出前完成 SQLite 外键恢复；若恢复失败则关闭并丢弃连接，命令失败，禁止把该连接交还业务池。失败状态如需持久化，须在原事务回滚及 FK 恢复后，以独立受保护事务记录安全状态，不保存原 SQL/值/连接串；记录失败不能掩盖原失败，下一次执行不得误判已应用。只有确认已回滚的失败可再次执行；失败的内容身份仍需核对，不能用修订同编号绕过漂移检查。

提交连接中断等结果未知时不写“已回滚”或“可安全重试”的假记录，也不返回成功；关闭连接，报告需再次通过 status/完整历史校验确认。专用连接断开会释放 PG 事务锁/SQLite 写锁，下一次执行重新获得锁并检查实际元数据。已经应用的版本不会重复执行。

`db status` 只读取与校验，显示选定后端、前缀、版本和状态等安全摘要；不创建数据库、元数据表或“修复”历史。空库可显示未初始化/pending；无法连接、结构不兼容、内容漂移或错误状态明确失败。`db migrate/status/seed` 均拒绝预留 mysql8，不提供跨后端数据迁移。

## 6. A02 配置前置和启动边界

依据 02 §4 与本轮用户指定优先级，三个可执行共用一套加载器：安全默认值 < 配置文件/版本化模板 < Git 忽略的 `config/local.toml` < 环境变量 < Secret 注入。`BBBCM_CONFIG` 保留为显式配置文件入口；显式路径不存在必须报错。每层严格验证未知键和非法类型，不能让后层覆盖掩盖前层拼错的键。

四环境只允许 development/test/staging/production；模板不含真实部署值或 Secret。生产前缀固定 bcm_；mysql8 明确拒绝；后端所需连接参数、连接数、SQLite 文件路径、Redis URL/启用组合、worker.embedded 与程序类型都完整校验。SQLite 单写者且 embedded worker 与独立 worker 互斥（02 §6.4）。staging/production 拒绝开发演示、弱安全值和未解析占位符，不从开发默认参数猜测待批准生产容量。

PostgreSQL 连接串仅经 `BBBCM_DATABASE_POSTGRES_URL` 或对应 Secret 注入获得，不允许配置文件字段携带；Redis 和已接入组件的秘密同样只经注入边界。Secret 的 Debug、错误、日志均为固定脱敏文本，不回显输入、解析片段或底层连接错误中的凭证。未批准 provider 缺失时保持关闭，不新增虚构默认配置或认证功能。

数据库连接/能力探测遵守 02 §4/6.5：PostgreSQL UTF-8 与非 C/POSIX lc_ctype 校验；pg_jieba/pg_trgm 缺失遵守 search 关闭语义，不静默替换检索路径；SQLite FTS5 临时探测失败只关闭该能力。迁移 bootstrap 是修复/建立结构的管理入口，不以业务表已存在为前置；服务启动与 CLI 命令各自需要的检查必须区分，不能用服务角色连接去执行迁移。

本轮无配置数据库写入、Flag set、/manage/config、管理审批、只读/紧急关闭运行时控制或新提示页。现有 Flag 继续全关，A00/A01 在 development/test 的夹具及 staging/production 的资产隔离保持不变。

## 7. A04 事务与固定锁顺序设计

本节细化 01 §7.3、02 §9/10 与 03 §4/9，供 A04 实现和领域命令复用。本轮不实现业务事务封装或领域写服务。

写命令携带 actor_id、request_id、idempotency_key、expected_entity_version、expected_actor_authz_version 与类型化载荷；管理命令还带 active_assignment_id、reason_code、ticket/case 引用、适用的重新认证与审批。解析与预读可在事务前完成，但所有可变权限事实必须在最终事务中重新读取。

每条命令先形成完整锁集合，再按以下总序取锁；同一类别内按受信表序及稳定主键升序，多个 actor/目标同时排序，禁止按用户提供数组顺序取锁。

| 顺序 | 锁类别 | 目的 |
|---|---|---|
| 1 | platform 的命令幂等记录，键按 `(scope, actor_id, key)` | 同一命令只存在一个确定结果；无副作用返回先核对请求 hash |
| 2 | IAM 授权上下文：员工身份、会话、分配/范围、权限版本、重新认证/审批 | 在状态变化前确认管理角色仍有效，重新认证和审批使用不被并发复用 |
| 3 | identity：用户/账号状态先按 ID，随后邀请码、一次性令牌、会话等受限对象按表与 ID | 稳定 actor/目标状态；邀请注册同时计划创建者配额和邀请码的锁集合 |
| 4 | trust：邀请配额/资格、风险状态；后续账本账户按 ID | 防重复消费，identity 调用 trust 受限写服务仍共用当前事务 |
| 5 | community：版块 → 主题 → 回复/修订/权威搜索行；同类按 ID | 版块权限与主题状态稳定，楼层从已锁主题的专用计数器分配 |
| 6 | media → interaction → moderation → support → privacy → operations → campaign → commerce → analytics，各域按受信表序与 ID | 跨领域命令保持同一总序，后续能力未启用时不产生对应锁或写入 |
| 7 | 不可变追加记录与结果：业务修订/账本分录、幂等结果、Outbox、审计 | 完成同一事务的事实及派生通知请求；不从此阶段反向获取较早类别锁 |

本总序是取锁顺序，不是 crate 调用顺序；Cargo DAG 仍遵守 02 §2.1。跨领域命令由发起 core 统一规划锁，受限写服务接受同一事务、复用已有锁，不因 moderation 调用 content 就先锁案件再锁主题。锁后才发现必须取更早类别的额外对象时，必须放弃当前事务，重新构造完整计划；不能反向追加锁。搜索权限投影与原内容同事务收紧，Outbox 不补写权威权限。

PostgreSQL 默认 READ COMMITTED，竞争点通过平台方言入口 FOR UPDATE，必要时才 SERIALIZABLE；lock_timeout 500ms，40001/40P01 最多有界重试 3 次且命令必须有幂等键。SQLite 统一 BEGIN IMMEDIATE、WAL、busy_timeout 5000ms，不模拟行锁，不做 PostgreSQL 序列化重试；BUSY/BUSY_SNAPSHOT 按后端分类在已确认回滚、幂等及预算条件下处理。唯一冲突不是死锁/序列化重试，按 02 §6.1 保存点方案或业务 409 处理。

实体 UPDATE 同时检查版本/If-Match，影响行数为 0 返回 409；不使用无条件覆盖。Repository 只借用当前事务连接，不能自行 COMMIT，也不能通过对方 repo 跨域写入。

## 8. 幂等、Outbox 与追加审计设计

### 8.1 幂等

未来幂等记录逻辑字段包含 scope、actor_id、key、规范化请求 hash、应用层生成的 operation_id、状态、最小响应摘要和创建/完成/过期时间，唯一键为 `(scope, actor_id, key)`。同 key 同 hash 返回原响应；同 key 异 hash 返回 409，不再次执行业务。幂等记录与业务状态、版本、Outbox、适用审计同事务提交。

客户端成功只对应确定提交。提交阶段连接断开返回 202 与提交前生成的 operation_id，状态查询仍校验原 actor、scope 与幂等键；operation_id 单独不能成为越权查询凭据。普通响应保留 30 天（01 §7.3），到期清理响应不能清除邀请消费、处罚、角色变更、积分或活动资格的业务唯一事实。过期后能否再次执行由业务约束判定，不因清理幂等缓存恢复已消费资格。

平台 upsert 只能采用保存点 INSERT 优先/冲突回滚保存点后 UPDATE，或明确无竞争的两步方案；PG 唯一冲突使事务 aborted，不能直接继续 UPDATE。主键回读统一通过平台同事务同连接接口；批量插入通过应用预定稳定唯一键回查。本轮 seed 的 slug/版块版本回查符合该原则，但不等于 A04 通用引擎已交付。

### 8.2 Outbox

未来事件含 UUIDv7 event_id、聚合类型/ID、事件类型、版本、UTC 微秒时间、最小脱敏 TEXT JSON payload、trace/request 摘要；禁止密码、令牌、有效邀请码、邮件正文、证件及原始 C3。业务状态在主库提交时已经正确，Worker 只处理邮件、通知、媒体、统计、缓存失效等已提交副作用。

sink 用 `(sink, event_id)` 唯一约束去重，状态包含租约、续租、重试/退避、DLQ 和人工重放边界。PostgreSQL FOR UPDATE SKIP LOCKED 集中在方言层；SQLite 单写者按“取 ID 批→按 ID 更新租约并核对行数→按 lease_batch_id 回读”，lease_batch_id 为应用 UUIDv7；lease_owner 只用于诊断，不能代替批次回读。不得使用 RETURNING 或 IN 子查询 LIMIT。外部副作用暂停不回滚已提交业务事实。

### 8.3 追加审计与敏感读取

未来 AuditEvent/SensitiveAccessEvent 保存 actor 摘要、目标类型/ID、动作、理由代码、必要说明、工单/案件、UTC 时间、结果、操作/追踪关联及必要版本；不记录敏感原文或 secret。高危写入和审计同事务，审计失败整个命令失败关闭（ADMIN-012）。敏感读取在同一短事务内重新授权与追加访问审计，审计提交失败不返回数据（01 §3 管理授权边界，03 §8）。

数据库 ACL 不允许 runtime 修改或删除审计历史；更正用新的补偿/更正事件引用原事件，不 UPDATE 旧事件。审计的独立权限域复制由 Outbox 驱动，provider 未批准时保持关闭；本地原子审计仍是前提，不能以“将来异步记录”替代。审计缩短保留或删除需要双人审批并留下外部审计事件（01 §4.16），不会作为普通 worker 清理权限授出。

业务 IAM 使用 RBAC 能力上限 + ABAC 当前资源关系；一个管理会话只激活一个角色，MFA、分配/会话/范围版本与期限逐次校验；申请人/操作者/审批人关系由服务端验证，不允许自批。C3 永不由 /manage 页面/API 返回，数据库读权限也不能绕过应用字段裁剪与用途授权。
