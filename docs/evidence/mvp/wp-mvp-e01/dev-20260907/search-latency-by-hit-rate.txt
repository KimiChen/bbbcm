# 搜索延迟按命中率分档（2026-09-07）

上一轮 A/B 只测了两个极端——命中率 0% 与 100%——并据此写下「零命中已解决、全量
命中是最坏边界、不代表典型负载」。**中间档位推翻了这个乐观判断。**

环境：生产近似规格（4 vCPU / 8 GiB、NVMe 持久挂载、`fsync=on`、
`synchronous_commit=on`、`shared_buffers=2.5GB`），**GIN 索引已建**，干净前缀，
16 路并发 × 每路 20 次，每页取前 50。

命中率由播种时按 `n % 10 / 100 / 1000` 注入互不共字的标记词实现，并在测量前
**回读真实命中数**核对——档位标签必须是实测值，不是请求值。

## 结果（100,000 篇，已建索引）

| 命中率 | 实测命中 | p50 | p95 | p99 | 对 400ms 门槛 |
|---|---:|---:|---:|---:|---|
| 0%（「紫檀」） | 0 | 8.3ms | 87.2ms | 4748.1ms | **通过** |
| 0.1%（「山竹」） | 100 | 9.5ms | 21.2ms | 40.2ms | **通过** |
| 1%（「猕猴桃」） | 1,000 | 92.4ms | **1395.4ms** | 2040.9ms | **超 3.5 倍** |
| 10%（「蓝莓」） | 10,000 | 230.4ms | **2101.6ms** | 4016.6ms | **超 5.3 倍** |
| 100%（「曼陀罗」） | 100,000 | 2082.7ms | **3299.6ms** | 3590.2ms | **超 8.2 倍** |

对照 2,000 篇（同环境、同索引）：五档全部通过，p95 最高 84.9ms。

## 结论必须更正

上一轮写的「全量命中一列是上界压力测试，不代表典型负载会是 4 秒」**过于乐观**。
实测的分界线不在 100%，而在 **0.1% 与 1% 之间**：

- 命中 100 条：21.2ms，余量 19 倍。
- 命中 1,000 条：1395.4ms，超标 3.5 倍。

**1,000 条命中是完全普通的搜索结果规模。** 十万篇语料里一个词命中 1%，在中文
论坛上是常见而非极端——「显卡」「续费」「报错」这类词都会落在这个量级。因此这
不是「最坏边界不达标」，而是**大多数真实查询都不达标**。

按 `90` §6 的百万级基线外推，1% 命中意味着 10,000 条匹配，只会更差。

## 根因：索引解决了查找，解决不了查找之后

`platform::db::full_text_search_sql` 生成的查询形状是：

```sql
SELECT DISTINCT d.topic_id, d.title, d.forum_id, t.created_at
  FROM search_documents d JOIN topics t ON t.id = d.topic_id
 WHERE (to_tsvector(...) @@ ... OR to_tsvector(...) @@ ...)
   AND <可见性/审核/删除/版块/时间 过滤>
 ORDER BY t.created_at DESC, d.topic_id DESC
 LIMIT 50
```

GIN 索引让 `@@` 这一步很快，但之后仍要：**取回全部 N 条匹配 → 与 `topics` 连接 →
`DISTINCT` 去重 → 按 `created_at` 全量排序 → 取前 50**。这几步的代价随 N 线性或
`N log N` 增长，与索引无关。排序键 `created_at` 在 `topics` 上而不在
`search_documents` 上，因此**必须先连接才能排序**，排序无法提前截断。

零命中与 0.1% 之所以快，正是因为 N 小到这几步不要钱。

## 可选修法（未实施，属设计决策）

1. **把排序键物化进 `search_documents`**。`created_at` 进检索文档表，配
   `(created_at DESC, topic_id DESC)` 索引；排序不再需要连接 `topics`，规划器有
   机会按时间序扫描并在凑满 50 条后停止。`search_documents` 本就已冗余 title、
   body、visibility、forum_id，加一列与现有设计一致。代价是多一个需要与主题同步
   的冗余字段。
2. **改按相关度排序并截断**（`ts_rank` + 候选集上限）。能把成本压到与候选上限
   相关，但**改变了产品语义**——`SEARCH-*` 当前按时间倒序，改成相关度是产品决策。
3. **引入 RUM 扩展**：索引内携带排序载荷，可直接按时间序返回。效果最好，但新增
   一个第三方 C 扩展依赖，与 `pg_jieba` 同类的维护与镜像构建成本。
4. **接受现状并降低门槛**：把搜索从「公开读 p95 ≤ 400ms」中拆出，单列更宽的门槛。
   这是改事实源，不是改实现。

`DISTINCT` 也值得单独看：`search_documents` 每帖一行，同一主题的多个帖子会产生
重复 `topic_id`，`DISTINCT` 因此要对全部匹配做去重。若第 1 条落地，可考虑同时按
主题维度建一张去重后的检索投影。

## 一处未解释的观察

零命中档的 p99 为 4748.1ms，而 p50 仅 8.3ms、p95 87.2ms——320 个样本里的孤立离群
值。本轮已把预热从「只热一个词」改为**逐词预热**（此前只热「曼陀罗」，其余各档的
首次查询仍在付冷启动的钱），改后该离群值仍在。它不随命中率变化，形态更像检查点
或 autovacuum 造成的停顿，而非查询本身的成本。未进一步定位。
