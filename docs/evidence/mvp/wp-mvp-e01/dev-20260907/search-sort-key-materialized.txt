# 排序键物化：五档实测与一处新暴露的瓶颈（2026-09-07）

按 `DEC-069` 补充裁决实施「排序键物化进检索表」：`created_at` 写入
`search_documents`（迁移 0022），配 `(created_at, topic_id)` 索引，
`full_text_search_sql` 不再连接 `topics`。

环境与前一轮完全相同（生产近似规格、GIN 已建、干净前缀、100,000 篇、16 路并发）。

## 五档前后对比

|---|---:|---:|---|
| 0%（「紫檀」） | 87.2ms | 83.9ms | 持平 |

超门槛档位由 **3 个减为 1 个**。10% 与 100% 两档从超标 5–8 倍变为余量 4–26 倍。

## 计划确认修法本身是对的

`EXPLAIN (ANALYZE, BUFFERS)` 于 1% 档：

```
Limit (actual time=722.146..731.840 rows=50)
 -> Unique
   -> Incremental Sort   Presorted Key: created_at, topic_id
     -> Gather Merge (Workers Launched: 2)
       -> Parallel Index Scan Backward using search_sort_idx on search_documents d
            Filter: (publication = … AND moderation = … AND deleted_at = …
                     AND (to_tsvector('jiebaqry', title) @@ … OR to_tsvector('jiebaqry', body) @@ …))
            Rows Removed by Filter: 12865
```

结构正是设计意图：**按排序键有序扫描、凑满 50 条即停**，不再全量排序，
`Incremental Sort` 只对预排序键之外的列做局部排序（Full-sort Groups: 2）。
高命中率因此变快两个数量级——匹配密集时，扫几十行就能凑够 50 条。

## 1% 档为什么反而变慢

慢的不是扫描本身，是**过滤谓词**：

```
Rows Removed by Filter: 12865   （每 worker，三路合计约 38,600 行）
```

每扫一行都要**重新对正文做一次 jieba 分词**再判 `@@`。1% 命中意味着平均每 100 行
才中一条，要凑 50 条就得扫几千行，每一行都付一次分词的钱。单次执行 731ms、
16 路并发下 p95 2400ms，正是这笔 CPU 开销被并发放大的结果。

修前该档走的是 GIN + 全量排序（1395ms）；修后规划器改走有序扫描，两条路都贵，
只是贵在不同地方。**这不是修法选错，而是它暴露了下一层瓶颈**：

- 高命中率：扫描少，分词次数少 → 快。
- 零命中／极低命中率：GIN 直接定位，扫描路径不被选中 → 快。
- 中间带（约 1%）：两条路都不理想——GIN 要排全量，有序扫描要重算几千次分词。

## 根因是「每次查询都重算分词」

`to_tsvector('public.jiebaqry', d.body)` 是表达式，既用于 GIN 表达式索引，也用于
顺序/索引扫描时的过滤。**表达式索引只能加速索引查找，不能免除过滤路径上的重算。**

标准做法是把 tsvector 物化成一列并在其上建 GIN：GIN 查找与过滤判定都读同一列，
两条计划都不再分词。该列依赖 `pg_jieba`，因此属 `postgres-search` 轨而非基线轨。

下一步实施该列。本文件记录的是排序键这一步的独立效果。
