# DEC-068 顶级版块路由：真实 PostgreSQL 实测（2026-09-07）

环境：远端 Docker PostgreSQL 16（`bbbcm-postgres:m0-03-x86_64`，UTF8 / C.UTF-8），
经本机回环 SSH 隧道访问；独立随机 schema 前缀，`app_login` 运行角色仅属 `app_rw`
一个组。连接串与主机地址一律走环境变量，不入库。

## 迁移与种子

```
迁移完成：应用 [1 .. 21]；已应用跳过 []
种子完成：新增 6 个版块、6 个规则占位版本；已有数据保留
```

种子写入的六个版块 `status = 'draft'`（开发种子的既定行为，规则仍是占位版本），
因此默认不出现在目录里。本次为验证版块页把它们改为 `active`。

## 路由实测

| 路径 | 状态 | 说明 |
|---|---|---|
| `/daily` `/showcase` `/ai` `/hosting` `/releases` `/meta` | 200 | 六个版块页全部可达 |
| `/nope` | 404 | 未知 slug 不回落到首页 |
| `/forums/daily` | 404 | 旧形状已不是任何路由 |
| `/new` `/search?q=x` | 200 | 静态段优先于参数段，未被版块段吃掉 |
| `/daily/feed.xml` | 200 | 版块订阅源 |
| `/feed.xml` | 200 | 全站订阅源 |
| `/nope/feed.xml` | 404 | 未知版块的订阅源不回落成全站源 |

页面标题分别为「日常 · 草莓论坛」「AI · 草莓论坛」「站务 · 草莓论坛」，
说明 slug 确实参与了过滤而不只是渲染了同一个列表。

主导航实际渲染七项：「全部主题」加六个版块，链接为 `/daily?theme=system` 等。

## 本次实测发现并修复的缺陷

改路由时只改了路由表，没改处理器里的路径分发。处理器按 `parts[0] == "forums"`
的**两段**形状取 slug，改成顶级单段后这个分支再也匹配不到，于是 `/daily` 与
`/nope` 全部落进 `_ => "最新回复"` 兜底分支——两者返回 **200 且内容与首页相同**。

失败形态值得单独记一笔：它不报错。打错的链接、被删的版块、权限不足三种情况
一律渲染成一个看起来完全正常的页面，页面里没有任何线索说明你并不在自己以为的
那个版块。修复为单段 slug 分支并在找不到时 404；订阅源同步改为按段数判定。

## 回归防护

`crates/content/src/http.rs` 新增 `every_top_level_static_route_is_a_reserved_forum_slug`：
从真实路由表逐条推导顶级静态段，断言每一条都无法被建成版块 slug。不抄清单，
将来新增顶级路由却漏登记保留字时这条测试会失败。

已做变异验证：从保留字清单删掉 `hot` 后测试如期失败并指名该段；恢复后通过。
测试另有防空断言（至少检查到 10 条），避免过滤条件写错导致一条不跑却「通过」。
