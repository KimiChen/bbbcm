# 公开读吞吐基线：200 read/s 首次实测（2026-09-07）

`90` §6 的「公开读负载 200 read/s 起点」此前从未测量过。本文件是第一次。

## 与既有延迟数据的关系

此前所有性能数字来自 `crates/content/tests/postgres_performance.rs`，那是**固定
并发下的延迟测量**，不是吞吐测试：

| | 延迟载体 | 本载体 |
|---|---|---|
| 发压方式 | 16 路背靠背（闭环） | 固定 200 req/s（开环） |
| 速率 | 由系统快慢决定，不受控 | 由载体决定，系统慢也不减速 |
| 被测层 | `ContentService` 领域读路径 | Axum handler + Askama 渲染 + HTTP |
| 时长 | 320 次请求，常不足 1 秒 | 每路径 12,000 次，60 秒发压窗口 |

闭环测不出吞吐：系统一慢请求自然变少，负载跟着塌下去，测出来的永远是「系统当前
能做到的速率」而不是「能不能扛住目标速率」。

## 环境：应用与数据库同机

此前的测量隔着 SSH 隧道（应用在 macOS 本机、数据库在远端），与生产单 VPS 拓扑
不符，该限制登记在 `DEC-069`。本轮全部在一台专用 Linux 测试主机上完成（主机标识按公开仓库规则脱敏，规格如下，可据此复现）：

| 项 | 取值 |
|---|---|
| 宿主 | Linux 7.0.0-31，18 核 / 30 GiB |
| PostgreSQL | Docker 容器，配额 4 vCPU / 8 GiB，NVMe 持久绑定挂载 |
| PG 参数 | `fsync=on`、`synchronous_commit=on`、`shared_buffers=2GB`、`max_connections=200`、`random_page_cost=1.1`（`DEC-069`） |
| 应用 | 同机 `bbbcm-web`，**release 构建**，连接 `127.0.0.1:5434`，无隧道 |
| 应用连接池 | 32 |
| 数据量 | 100,000 篇检索文档（`DEC-070` 基线） |

同机后播种耗时由隧道版的 490–508s 降到 **171.1s**，接近 3 倍——隧道对写入影响
不小，此前的写入相关观测都受它影响。

## 本文件前半部分的数字全部作废

写在最前面，因为它影响本文件此前的每一个结论：**载体从不灌 `topic_history`，
主列表一直在渲染 0 行主题。**

`repo::candidates()` 把 `topics` 与 `topic_history` 做 JOIN，且只取
`sequence_no <= commit_state` 水位的行。载体两样都没做——既不插历史行，水位也停在
0。于是 `/`、`/new`、版块页渲染的是空列表，而 `/hot` 走 `view_count` 排序、不依赖
该表，是唯一渲染真实 50 行的路径。

同一实例上的对照：

| 路径 | 数据库查询数 | 渲染主题行 |
|---|---:|---:|
| `/`（修复前） | 20 | **0** |
| `/hot`（修复前） | 416 | 50 |

差距不是 `/hot` 慢，是 `/` 根本没取到数据。据此得出的「`/` 与 `/new` 在 100 req/s
下 p95 8.4／9.0ms、余量 48 倍」测的是空页面；「200 read/s 饱和在 128 req/s」里
`/` 与 `/new` 那两条同样作废。

**还有第二个作废原因**：`runweb.sh` 的 `pkill` 模式被一次 `sed` 连同可执行路径一起
改写，旧的 **debug** 进程没有被杀、继续占着端口，新起的 release 进程绑不上就退出。
因此所有标称 release 的测量实际都跑在 debug 上，「debug 与 release 差别可忽略」这个
结论也随之作废——修正后实测 `/` 空页面 debug 33ms、release 7.3ms，差 4.5 倍。

两处都已修（载体补 `topic_history` 与水位并加防空断言；`runweb.sh` 改用
`pkill -x` 按进程名精确匹配）。以下是修复后重测的结果。

## 结果：列表页在**完全空载**下就已超出门槛

环境：应用与数据库同机、**确认为 release 二进制**、连接池 32、10 万主题、
`topic_history` 与水位齐备、四个页面各渲染 50 行、机器 load < 1.5。

| 路径 | 渲染行数 | 空载单请求 |
|---|---:|---:|
| `/` | 50 | **0.851s** |
| `/new` | 50 | **0.859s** |
| `/hot` | 50 | **0.527s** |
| 版块页 | 50 | **0.880s** |

**四条路径在零负载下的单次请求就已超过 `90` §6 的公开读 p95 400ms 门槛**，是它的
1.3–2.2 倍。加负载只会更差：目标 10 req/s 时实际只跑到 **2.2 req/s**，p95 **116 秒**。

## 根因：列表页每次渲染发约 820 条数据库查询

对首页一次请求抓全部语句并归类：

```
300 × SELECT public_id, username, status, ... FROM identity.users WHERE id = $1
200 × SELECT * FROM community.topics WHERE id = $1
200 × SELECT * FROM community.posts  WHERE topic_id = $1 AND floor_no = $2
100 × SELECT tag_id FROM community.topic_tags WHERE topic_id = ...
  4 × 真正的列表查询（keyset 分页）
———
约 820 条
```

每条单独看都很快（最慢 0.111ms），问题是**数量**：列表查询取回 50 个 ID 之后，
逐条去查主题、首帖、作者与标签——教科书式的 N+1，只是倍数是 8 而不是 1。
820 × 约 1ms 的往返 ≈ 820ms，与实测的 851ms 吻合。

三条路径的查询数几乎相同（822／817／817），说明这不是某个页面的特例，而是**共用
的取数路径**如此。

## 这个缺陷为什么一直看不见

- 领域层的延迟载体用的是小夹具，50 条 N+1 在几十行数据上只有毫秒级差别；
- HTTP 层的吞吐载体因为 `topic_history` 空缺，列表一直是 0 行，N+1 从未被触发；
- 页面本身渲染正常、返回 200、无任何错误或告警。

三个条件叠加，使一个「每次页面渲染发 820 条查询」的问题在所有既有验证里都不显形。

## 已修的两处（效果确凿，但不解决上面的 N+1）

**`max_connections = 1` 是默认值**：那是 SQLite 的默认值，切 PostgreSQL 忘了改就
只有一条数据库连接、全部请求排队，不报错不告警。200 req/s 下服务端单请求由 5.7 秒
降到 1.6 秒。已加启动校验拒绝 `postgres + max_connections < 2`。

**`/hot` 的 `view_count` 无索引**：`DEC-030` 的累计阅读量降序原本对 10 万行全表
扫描加排序。建 `(view_count, id)` 后该查询由 12 秒级降到 **0.074ms**（`EXPLAIN
ANALYZE` 实测走 `Index Scan Backward using topic_hot_idx`）。

**站点统计的三条全表 COUNT**：加了 30 秒 TTL 缓存并已验证生效（首次请求 3 条
COUNT，随后为 0）。但它对总量的贡献很小——820 条里只占 3 条。

## 载体本身修的三处

本轮暴露出的载体缺陷都属同一类：**数字看着合理，测的却是另一件事**。

1. `seed()` 只插不清，同一前缀重复运行会累积，把 21.2 万行的表报成「2,000 档」。
   已改为回读并返回真实行数。
2. `runweb.sh` 的 `pkill` 模式被 `sed` 连带改写，测的一直是 debug 二进制。
   已改用 `pkill -x` 按进程名精确匹配。
3. 从不灌 `topic_history`，主列表恒为空。已补插入与水位推进，并加防空断言——
   水位内没有历史行时直接失败，并写明「空页面的延迟数字没有意义」。

另补一条对账断言：实测出现过「300 次发出只回收 105 个样本、错误却是 0」的情况，
那 195 次没有任何记录，而缺失的多半是最慢的那些，留着会让 p95 系统性偏低。现在
`样本数 + 错误数 != 发出数` 直接失败。

## 效力与结论

规格已获批准（`DEC-069`）、基线为 10 万（`DEC-070`）、目标为 100 read/s
（`DEC-071`），本组结果具备门禁效力。

**`90` §6 的公开读 p95 400ms 与 100 read/s 两项门槛均未通过**，且差距不在配额而在
实现：列表页的 N+1 取数需要改为批量加载。这是本轮发现的最主要缺陷，未修复。

## 尚未覆盖

- SSR 首屏 p95：本载体覆盖完整渲染路径，但在当前 N+1 未修的状态下测它没有意义。
