# 公开读吞吐基线：200 read/s 首次实测（2026-09-07）

`90` §6 的「公开读负载 200 read/s 起点」此前从未测量过。本文件是第一次。

## 与既有延迟数据的关系

此前所有性能数字来自 `crates/content/tests/postgres_performance.rs`，那是**固定
并发下的延迟测量**，不是吞吐测试：

| | 延迟载体 | 本载体 |
|---|---|---|
| 发压方式 | 16 路背靠背（闭环） | 固定 200 req/s（开环） |
| 速率 | 由系统快慢决定，不受控 | 由载体决定，系统慢也不减速 |
| 被测层 | `ContentService` 领域读路径 | Axum handler + Askama 渲染 + HTTP |
| 时长 | 320 次请求，常不足 1 秒 | 每路径 12,000 次，60 秒发压窗口 |

闭环测不出吞吐：系统一慢请求自然变少，负载跟着塌下去，测出来的永远是「系统当前
能做到的速率」而不是「能不能扛住目标速率」。

## 环境：应用与数据库同机

此前的测量隔着 SSH 隧道（应用在 macOS 本机、数据库在远端），与生产单 VPS 拓扑
不符，该限制登记在 `DEC-069`。本轮全部在一台专用 Linux 测试主机上完成（主机标识按公开仓库规则脱敏，规格如下，可据此复现）：

| 项 | 取值 |
|---|---|
| 宿主 | Linux 7.0.0-31，18 核 / 30 GiB |
| PostgreSQL | Docker 容器，配额 4 vCPU / 8 GiB，NVMe 持久绑定挂载 |
| PG 参数 | `fsync=on`、`synchronous_commit=on`、`shared_buffers=2GB`、`max_connections=200`、`random_page_cost=1.1`（`DEC-069`） |
| 应用 | 同机 `bbbcm-web`，**release 构建**，连接 `127.0.0.1:5434`，无隧道 |
| 应用连接池 | 32 |
| 数据量 | 100,000 篇检索文档（`DEC-070` 基线） |

同机后播种耗时由隧道版的 490–508s 降到 **171.1s**，接近 3 倍——隧道对写入影响
不小，此前的写入相关观测都受它影响。

## 结果

目标 200 req/s × 60s，每路径 12,000 次请求，release 构建，池 32，两处修复后：

| 路径 | 实际速率 | p50 | p95 | 200 响应 | 错误 |
|---|---:|---:|---:|---:|---:|
| `/`（首页） | **128.1 req/s** | 18500.8ms | **32649.7ms** | 12000 | 0 |
| `/new` | **127.6 req/s** | 18499.2ms | **33056.4ms** | 12000 | 0 |

**200 read/s 不成立。** 系统饱和在约 128 req/s；超出部分持续堆积，60 秒窗口内积压
到几十秒的等待。所有请求最终都返回 200、零错误——它不是崩溃，是排队。

p95 高达 30 秒是**开环 + 从计划发出时刻起算**的必然结果，也正是这种测法的价值：
闭环会把这段排队时间从统计里抹掉（coordinated omission），报出一个漂亮的 p95。

## 根因：PostgreSQL 容器的 4 vCPU 已经跑满

负载中实测容器 CPU：

```
docker stats bbbcm-e01-perf
CPU=402.86%   CPU=402.85%   CPU=403.43%     配额 4 vCPU = 400%
```

**100.7% 饱和，没有余量。** 与算术完全吻合：

每请求的数据库 CPU 由饱和点直接推出，不依赖对空载时间构成的猜测：

| 量 | 值 | 来源 |
|---|---|---|
| 容器 CPU | 402.86% / 400% | `docker stats` 实测 |
| 实测吞吐 | 128 req/s | 载体实测 |
| 每请求数据库 CPU | 4 ÷ 128 ≈ **31ms** | 由上两行相除得出 |
| 空载单请求端到端 | 33ms | `curl` 实测 |

两个独立来源的 31ms 与 33ms 吻合，互为佐证：**请求的时间几乎全部是数据库 CPU**，
应用侧渲染与 HTTP 开销只占 2ms 量级。

即：**在当前的每请求数据库成本下，4 vCPU 的算术上限就是约 130 req/s。**
要达到 200 read/s，需要 200 × 0.031 ≈ **6.2 vCPU**，或者把每请求数据库成本压到
20ms 以下，或者在页面层加缓存。

### debug 与 release 几乎无差别，排除了渲染开销

同配置下 debug 125.0 req/s、release 128.2 req/s。若瓶颈在模板渲染或序列化，
release 应有数量级改善。差异可忽略即说明开销在数据库侧，这一条排除了「换 release
就好了」的猜测。

## 三处已定位成因，两处已修

### 一、`max_connections = 1` 是默认值（已修，效果确凿）

`config/default.toml` 的 `max_connections = 1` 是给默认后端 SQLite 的（单写者，
必须为 1）。切到 PostgreSQL 忘了改，应用就只有一条数据库连接，全部请求在它上面
排队——不报错、不告警，只是慢。同一份代码 200 req/s 下：

| 池大小 | 服务端单请求 |
|---|---|
| 1（默认） | **5.7 秒** |
| 32 | **1.6 秒** |

差 3.6 倍，唯一区别就是这个值，而 1 是默认值——「什么都不配」正好落在最差那一档。
已加启动校验：`backend=postgres` 时拒绝 `max_connections < 2`。只拒绝显然错误的
1，不规定具体取值——池规格属 `02` §19 的 `DEC-004-B/013`，未批准前不设默认。

### 二、`/hot` 的 `view_count` 上没有索引（已修，效果确凿）

`DEC-030` 定义首页「热门」为累计阅读量降序。`topics` 上原有三个索引——主键
`(id)`、`(forum_id, create_seq, id)`、`(author_id, create_seq, id)`——**没有一个
覆盖 `view_count`**，于是每次请求都要对 10 万行全表扫描加排序。

| | `/hot` 空载单请求 |
|---|---|
| 无索引 | **12 秒级** |
| 建 `(view_count, id)` 后 | **0.158s** |

同批空载对照：`/` 0.033s、`/new` 0.034s、版块页 0.032s。`/hot` 仍是最慢的一条，
但已不再是数量级差距。

### 三、站点统计的三条全表 COUNT——**假设错误，实测无改善**

`content::repo::site_statistics` 在每次页面渲染时执行三条 COUNT（主题、回复、
用户），无缓存。我据此判断它是首页瓶颈，实现了 30 秒进程内 TTL 缓存。

**实测吞吐没有变化**：加缓存前 `/` 为 128.3 req/s，加缓存后 128.1 req/s。
空载单请求也一样是 33ms。结论：**这三条 COUNT 不是瓶颈**，PostgreSQL 用索引扫描
就能算完，占不到每请求 33ms 的显著份额。

该缓存本身是合理改动（少三条查询、有 TTL 与失效边界测试），但它**没有解决它被
引入时声称要解决的问题**。这里如实登记，以免日后有人把吞吐数字的改善归给它——
吞吐的改善来自前两项，与它无关。

## 尚未覆盖

- `/hot` 与版块页的负载下数字：前一轮因残留进程污染作废，本轮仍在跑，另行补记。
- 写负载 20 write/s 与写 p95 未测。
- SSR 首屏 p95 名义上由本载体覆盖（含渲染与 HTTP），但系统饱和时这个数字只反映
  排队；须在不过载的速率（如 100 req/s）下另测。
- 本载体每请求新建一条 TCP 连接（发了 keep-alive 头但未复用）。真实客户端会复用，
  因此这是**偏保守**的模型，多付了握手成本。

## 一处测量纪律

中途一次测量得到 `/` 空载 2.89s、`/hot` 3.27s 的异常值，排查发现是上一轮被 kill
的测试进程仍在后台跑、机器 load 达 25。清理并等 load 降到 1.3 后复测，恢复为
0.033s／0.158s。**本文件中的所有数字都取自 load < 1.5 的静默机器**；那批污染值
不作数，登记在此以说明为何中途出现过不一致的读数。

## 效力

规格已获批准（`DEC-069`），基线已定为 10 万（`DEC-070`），本组结果具备门禁效力。

**`90` §6 的 200 read/s 公开读门槛未通过，且不是靠改代码能通过的**——它受限于
批准规格的 CPU 配额。可选路径三条：提高 CPU 配额到 ≥8 vCPU、把每请求数据库成本
压到 20ms 以下、或在页面层引入缓存。属设计决策，未自行选择。
