# WP-MVP-E01／E02 公开读延迟基线（2026-09-07）

载体：`crates/content/tests/postgres_performance.rs`，默认 `#[ignore]`。

## 效力声明（先于结论）

`90` §6 表末写明：「测试报告必须说明地区、设备、缓存冷热、连接池、数据分布、
测量窗口和资源规格。**规格未批准时只能形成实验结果，不能支持 Production
Approved**。」

本次运行的资源规格**尚未获批准**，因此下列数字是实验结果，不构成门禁依据。
载体已把全部条件打印在输出里，便于日后在批准规格上复跑比对。

## 运行条件

| 项 | 值 |
|---|---|
| 主机 | CPU 18 核；内存 30 GiB；Ubuntu 26.04.1 LTS |
| 数据库 | PostgreSQL 16.15（自建 pg_jieba 镜像），容器内，`shared_buffers=2GB`，`fsync=off`、`synchronous_commit=off`（一次性实例，非生产配置） |
| 数据目录 | tmpfs 6GB，即数据全在内存——这一点显著影响结果，生产磁盘不会如此 |
| 连接 | 本机回环经 SSH 端口转发；运行身份 `app_rw` |
| 连接池 | 上限 16 |
| 缓存 | 无应用层缓存（未注入 Redis）；数据库缓冲池已预热（正式测量前先跑 16 次） |
| 地区 | 单机本地，无跨区网络 |
| 测量窗口 | 每个读路径 16 路并发 × 每路 20～30 次 |

## 结果

| 数据量 | 读路径 | n | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| 2,000 主题 | 公开列表（首页最新回复） | 320 | 6.2ms | 7.9ms | 119.0ms | 127.6ms |
| 2,000 主题 | 版块列表 | 320 | 7.2ms | 8.1ms | 8.7ms | 8.8ms |
| 100,000 主题 | 公开列表（首页最新回复） | 480 | 6.0ms | **7.4ms** | 136.8ms | 149.9ms |
| 100,000 主题 | 版块列表 | 480 | 6.4ms | **7.2ms** | 7.3ms | 7.7ms |

门槛：公开读 p95 ≤ 400ms。两个量级均**远低于门槛**。

## 两点观察

**延迟对数据量不敏感。** 主题数从 2,000 增到 100,000（50 倍），p95 从 7.9ms 降到
7.4ms——在噪声范围内。这与 keyset 游标分页的预期一致：查询按索引取固定条数，
代价与总量无关。若将来某次改动让首页开始随数据量变慢，这条基线会立刻显出来。

**p99 有尾巴，且只在首页列表上。** 119～137ms 的 p99 与 6ms 的 p50 差两个数量级，
而版块列表没有这个尾巴。预热只跑了并发路数那么多次，因此部分连接的首次查询
（连接建立 + 计划缓存冷启动）仍落在测量窗口内。这是测量方法的产物，不是首页
本身的抖动；若要把 p99 也纳入门禁，需要延长预热并单独说明。
